Temporal Trust

How Raptor tracks claim freshness — because a verified fact from last week is not the same as a verified fact from five minutes ago.

Temporal Trust

A trust boundary tells you how a claim was established. Temporal trust tells you whether that claim is still current. Both matter for operational decisions.

Freshness states

Every claim in Raptor carries a freshness state that updates automatically based on the time elapsed since verification:

| State | Meaning | Operator guidance |
|-------|---------|-------------------|
| FRESH | Within the source-specific freshness window | Act with confidence |
| AGING | Past 50% of the freshness window | Still valid, re-verification approaching |
| STALE | Exceeded the freshness window | Do not act without re-verification |
| INVALIDATED | Contradicted by newer evidence | Discard — newer evidence supersedes |

Freshness transitions are automatic. When a FRESH claim crosses the 50% threshold of its window, it becomes AGING. When it exceeds the window, it becomes STALE. No manual intervention required.

Source-specific windows

Different types of evidence go stale at different rates. Raptor defines freshness windows per source type:

| Source type | Freshness window | Rationale |
|-------------|-----------------|-----------|
| Execution events | 1 hour | System state changes rapidly after actions |
| Database queries | 4 hours | Operational data shifts through the day |
| Policy evaluations | 24 hours | Policies change infrequently |
| Attestations | 7 days | Signed attestations are durable evidence |
| External API responses | 1 hour | Third-party data has unknown update frequency |

These windows are defaults. Organizations can configure custom windows per source type through governance policies.

How freshness affects decisions

Temporal trust integrates with decision support. When stale claims are present in a response:

  • Decision confidence is reduced. A response grounded in stale evidence cannot produce a CLEAR confidence level regardless of other factors.
  • Actionability is downgraded. Stale claims shift the actionability from safe to review, signaling the operator to verify before acting.
  • Re-verification is suggested. The decision support metadata includes a stale_claims array identifying which claims need refreshing.
{
  "decision_support": {
    "confidence": "ADVISORY",
    "stale_claims": [
      {
        "claim": "Current alert count: 3 open",
        "source": "alert_system",
        "verified_at": "2026-05-20T09:15:00Z",
        "freshness": "STALE",
        "window": "1h"
      }
    ]
  }
}

Invalidation

A claim is INVALIDATED when newer evidence directly contradicts it. This is not time-based — it is evidence-based.

For example: a claim "Build #42 is passing" verified at 10:00 AM becomes INVALIDATED if a new execution event at 10:30 AM records "Build #42 failed." The newer evidence supersedes the older claim regardless of the freshness window.

Invalidated claims are preserved in the audit trail with their invalidation reason. They are never deleted.

Why temporal trust matters

Without temporal trust, a system can present verified-but-outdated information with the same confidence as verified-and-current information. An operator sees "Confirmed" and acts — not realizing the confirmation is from three days ago.

Temporal trust makes staleness visible. The operator sees not just what was verified, but when it was verified and whether that verification is still meaningful.
