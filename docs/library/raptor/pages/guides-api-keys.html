API Key Management

Create, scope, rotate, and revoke Raptor API keys for backend and CI integrations.

API Key Management

Raptor API keys authenticate backend services, CI pipelines, and SDK integrations. Keys use the rpt_ prefix and are stored as SHA-256 hashes — the plaintext key is shown exactly once at creation.

1. Create a key

Via API

curl -X POST https://raptor.harpyits.com/api/keys \
  -H "Authorization: Bearer your_clerk_jwt" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "production-backend",
    "scopes": ["all"],
    "expires_at": "2027-01-01T00:00:00Z"
  }'

Response:

{
  "ok": true,
  "key": "rpt_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6",
  "key_id": "uuid",
  "name": "production-backend",
  "prefix": "rpt_a1b2",
  "warning": "Store this key securely. It will not be shown again."
}

Copy the key value immediately. After this response, Raptor only stores the hash — there is no way to retrieve the full key.

Via Settings UI

  1. Open the Control Panel
  2. Navigate to Settings
  3. Click "Create API Key"
  4. Name the key and set optional expiration
  5. Copy the displayed key before closing the dialog

2. Key format

Keys follow the format rpt_ + 32 hex characters:

rpt_a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6

The first 8 characters (rpt_a1b2) are stored as a prefix for identification in the key list. The full key is never stored — only its SHA-256 hash.

3. Authentication

Use the key in either header:

# Authorization header
curl -H "Authorization: Bearer rpt_a1b2c3d4..." \
  https://raptor.harpyits.com/api/chat


X-Raptor-Key header

curl -H "X-Raptor-Key: rpt_a1b2c3d4..." \
  https://raptor.harpyits.com/api/chat

Keys inherit the permissions of the tenant that created them. Every request made with a key is attributed to the creating actor and tenant.

4. Scoping

Keys accept a scopes array at creation. If omitted, the default scope is ["all"].

{
  "name": "read-only-dashboard",
  "scopes": ["read"]
}

Scoped keys can only perform operations matching their granted scopes. Use narrow scopes for integrations that only need read access.

5. Expiration

Set expires_at (RFC 3339) to create time-limited keys:

{
  "name": "ci-pipeline-q3",
  "expires_at": "2026-09-30T23:59:59Z"
}

Expired keys are rejected at authentication time. They remain in the key list with their expires_at visible.

6. Rotation

Raptor does not have an in-place rotation endpoint. To rotate a key:

  1. Create a new key with the same name and scopes
  2. Deploy the new key to your integration
  3. Revoke the old key once traffic has migrated
# Revoke the old key
curl -X DELETE https://raptor.harpyits.com/api/keys/{old_key_id} \
  -H "Authorization: Bearer your_clerk_jwt"

For zero-downtime rotation, your integration should accept the key from an environment variable so the swap requires no code deploy.

7. Revocation

curl -X DELETE https://raptor.harpyits.com/api/keys/{key_id} \
  -H "Authorization: Bearer your_clerk_jwt"

Revoked keys are rejected immediately. The revocation timestamp is recorded in revoked_at.

8. Listing keys

curl -H "Authorization: Bearer your_clerk_jwt" \
  https://raptor.harpyits.com/api/keys

The response shows prefix, name, scopes, last-used timestamp, expiration, and revocation status for each key. The full key is never included.

{
  "ok": true,
  "keys": [
    {
      "id": "uuid",
      "name": "production-backend",
      "prefix": "rpt_a1b2",
      "scopes": ["all"],
      "last_used_at": "2026-05-21T14:30:00Z",
      "expires_at": "2027-01-01T00:00:00Z",
      "revoked_at": null,
      "created_at": "2026-05-01T10:00:00Z"
    }
  ]
}

9. Credit exhaustion behavior

When a tenant's credit balance reaches zero, API keys for that tenant are subject to the tenant's billing tier behavior — requests may be paused or capped depending on the plan. Keys themselves are not revoked; the billing layer controls access.

Hash-only storage

Raptor never stores plaintext API keys. The key creation flow:

  1. Generate 16 random bytes, hex-encode to 32 characters
  2. Prepend rpt_ prefix
  3. Compute SHA-256 hash of the full key
  4. Store the hash and the 8-character prefix
  5. Return the full key once in the creation response

If you lose a key, revoke it and create a new one.
