Authentication

Authenticate with Raptor using Clerk SSO, API keys, or the Founder Key.

Authentication

Raptor supports three authentication modes. Use whichever fits your context.

| Mode | Use case | Header |
|------|----------|--------|
| Clerk SSO | Production workspace users | Browser session cookie (automatic) |
| API keys | Programmatic access, CI/CD, integrations | Authorization: Bearer rpt_... |
| Founder Key | Development, emergency access, bootstrap | X-Raptor-Founder-Key: ... |

All three modes work against the same API surface. The identity provider is recorded in the audit trail so you can always trace who authorized a request.

Clerk SSO (production)

Clerk handles authentication for workspace users. Supported providers: Google, GitHub, Microsoft, and email/password.

Setup

Set three environment variables:

CLERK_SECRET_KEY=sk_live_...
CLERK_PUBLISHABLE_KEY=pk_live_...
CLERK_DOMAIN=your-app.clerk.accounts.dev

Users sign in through the workspace UI at http://localhost:4000 (self-hosted) or https://raptor.dev (cloud). Clerk issues a __session JWT cookie that Raptor validates on every request.

How it works

  1. User signs in via Clerk's hosted UI (OAuth or email).
  2. Clerk sets a __session cookie containing a signed JWT.
  3. Raptor validates the JWT against your Clerk domain on every API call.
  4. The user's Clerk ID, tenant, and role are extracted and recorded in governance events.

No application code is needed -- the browser handles the cookie automatically.

Without Clerk

If you omit all CLERK_* variables, Raptor runs in token-only mode. All API access uses API keys or the Founder Key. This is valid for self-hosted deployments that do not need SSO.

API keys

API keys are the primary method for programmatic access. Keys use the rpt_ prefix and are stored as SHA-256 hashes -- the plaintext key is shown exactly once at creation time.

Creating a key

curl -X POST http://localhost:4000/api/keys \
  -H "Content-Type: application/json" \
  -H "X-Raptor-Token: your-access-token" \
  -d '{"name": "ci-pipeline", "scope": "chat"}'

Response:

{
  "ok": true,
  "key": "rpt_a1b2c3d4e5f6...",
  "prefix": "rpt_a1b2",
  "name": "ci-pipeline",
  "id": "uuid-here"
}

Save the key value immediately. It cannot be retrieved again.

Using a key

Pass the key in the Authorization header:

curl -X POST http://localhost:4000/api/chat \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer rpt_a1b2c3d4e5f6..." \
  -d '{"message": "What is the deployment status?"}'

Or use the X-Raptor-Token header:

curl -X POST http://localhost:4000/api/chat \
  -H "Content-Type: application/json" \
  -H "X-Raptor-Token: rpt_a1b2c3d4e5f6..." \
  -d '{"message": "What is the deployment status?"}'

Managing keys

# List all keys (shows prefix and name, never the full key)
curl http://localhost:4000/api/keys \
  -H "X-Raptor-Token: your-access-token"


Revoke a key

curl -X DELETE http://localhost:4000/api/keys/{id} \
  -H "X-Raptor-Token: your-access-token"

Security model

  • Keys are hashed with SHA-256 before storage. The database never contains plaintext keys.
  • Only the rpt_ prefix (first 8 characters) is stored for identification.
  • Revocation is immediate -- the hash is deleted, not marked inactive.

Founder Key (development / emergency)

The Founder Key is a single shared secret for bootstrap access and emergency recovery. It bypasses Clerk but still passes through full governance -- every Founder Key action is audited.

Setup

Generate a SHA-256 hash of your chosen key and set it in the environment:

# Generate the hash
echo -n "my-secret-founder-key" | shasum -a 256

Output: 9f86d08... (use this hash)



Set in .env

RAPTOR_FOUNDER_KEY_HASH=9f86d08...

Using the Founder Key (API)

Pass the plaintext key in the X-Raptor-Founder-Key header:

curl -X POST http://localhost:4000/api/chat \
  -H "Content-Type: application/json" \
  -H "X-Raptor-Founder-Key: my-secret-founder-key" \
  -d '{"message": "System health check"}'

Using the Founder Key (browser)

The workspace UI provides a Founder Key login form. On successful login, a raptor_founder_key cookie is set for the session. CSRF protection is enforced on the login endpoint.

# Programmatic login (sets session cookie)
curl -X POST http://localhost:4000/api/auth/founder-key \
  -H "Content-Type: application/json" \
  -H "X-CSRF-Token: token-from-cookie" \
  -d '{"key": "my-secret-founder-key"}' \
  -c cookies.txt


Subsequent requests use the cookie

curl http://localhost:4000/api/nests \
  -b cookies.txt

When to use the Founder Key

  • Local development -- simpler than configuring Clerk.
  • Emergency access -- if Clerk is unavailable, the Founder Key still works.
  • Initial bootstrap -- set up the first organization before SSO is configured.

The Founder Key is not scoped to a tenant. It authenticates as the platform founder with full access. Do not share it or use it for routine operations in production.

Authentication in the audit trail

Every governance event records the authentication method:

{
  "identity_type": "clerk",
  "identity_id": "user_2abc...",
  "tenant_id": "org_xyz..."
}

The identity_type field is one of: clerk, founder_key, or api_key. This makes it possible to audit who authorized every governed response, regardless of authentication method.

Access token vs. API key

Two token types exist. Do not confuse them:

| Token | Set via | Purpose |
|-------|---------|---------|
| RAPTOR_ACCESS_TOKEN | Environment variable | Operator-level access for self-hosted deployments. Used with X-Raptor-Token header. |
| rpt_ API key | Created via /api/keys | Per-tenant programmatic key. Used with Authorization: Bearer header. Scoped, audited, revocable. |

For production integrations, prefer rpt_ API keys. The access token is a bootstrap mechanism for self-hosted operators.
