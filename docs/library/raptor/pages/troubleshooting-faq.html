FAQ

Frequently asked questions about Raptor's capabilities, requirements, and operational details.

FAQ

How long can records be retained?

It depends on the table type.

  • Immutable tables (execution events, build attestations, transparency log, authorization events, governance policies): indefinitely. These tables form the cryptographic hash chain and cannot be deleted without breaking chain integrity. There is no retention limit.
  • Mutable tables (conversations, uploads, cache, artifacts): configurable per tenant. Retention periods range from 30 days to indefinite. Auto-delete can be enabled per resource type via retention policies.

You configure retention policies in Settings > Privacy > Retention Policies.

What database does Raptor need?

PostgreSQL 16 or later. Any PostgreSQL instance will work — self-managed, AWS RDS, Google Cloud SQL, Railway, Supabase, Neon, or a local Docker container.

Raptor connects via a standard DATABASE_URL connection string:

postgresql://user:password@host:port/database

The database user needs permission to create tables, triggers, and enable Row-Level Security. Raptor runs its own migrations on startup.

Can I use my own AI providers?

Yes. Raptor uses a Bring Your Own Provider (BYOP) model.

You supply your own API keys for any supported provider — Anthropic, OpenAI, Google Gemini, or Together AI. Raptor routes requests to your chosen provider using your key. You pay the provider directly at their published rates.

Raptor charges a governance fee of $0.012 per governed response for the classification, policy enforcement, trust boundary assignment, and hash-chained audit trail. The governance fee is the same regardless of which provider you use or what the provider charges.

What happens when my credit balance runs out?

It depends on how the API key is configured.

  • Pause (default): Requests return a 402 Payment Required response. No provider calls are made. The governance layer records the pause event in the audit trail. Service resumes when credits are added.
  • Continue: Requests continue to be processed. The credit balance goes negative. This is useful for production systems that cannot tolerate interruption. Negative balances must be settled.

You configure this behavior per API key in Settings > API Keys.

Is my data isolated from other tenants?

Yes. Tenant isolation is enforced at the database level, not the application level.

  • 30 tables have PostgreSQL Row-Level Security (RLS) policies with FORCE ROW LEVEL SECURITY enabled
  • The database role used by the application sets the tenant ID at connection time — every query is automatically scoped
  • Even the database owner role is subject to RLS policies
  • A bug in application code cannot leak data across tenants because the database itself enforces the boundary

API keys, webhooks, policies, nests, execution events, and all other tenant data are scoped to a single tenant ID.

Can I export my data?

Yes. Raptor supports full data export in compliance with GDPR Article 20 (data portability).

GET /api/tenant/audit/export exports your complete tenant data in JSON format, covering 12 tables:

  • Execution events (the hash-chained audit trail)
  • Nests and conversation history
  • Governance decisions and policy evaluations
  • Authorization events
  • Artifacts and uploads
  • Provider call records
  • Cost events

You can also export per-nest data via GET /api/nests/{id}/verification for a single nest's chain and governance history.

What is the difference between Infrastructure and Workspace?

Same governance substrate, different consumption model.

| | Infrastructure | Workspace |
|---|---|---|
| Access | API-only | API + Control Panel UI |
| Authentication | API keys | Clerk SSO + API keys |
| Billing | Usage-based (per governed response) | Subscription + usage |
| Team | Not applicable — API keys are the identity | Owner, Admin, Member roles with RBAC |
| Use case | Embed Raptor governance into your own application | Use Raptor as a governed AI workspace for your team |

Both tiers get the same governance: classification, trust boundaries, policy enforcement, hash-chained audit, and cryptographic attestation.

How do I verify the hash chain?

Raptor exposes three public verification endpoints that do not require authentication:

GET /.well-known/raptor/attestation

Returns the Ed25519 build attestation for the current deployment, linking a specific Git commit to the running build.

GET /.well-known/raptor/transparency

Returns the transparency log — a public record of governance policy changes and significant system events.

GET /.well-known/raptor/trust

Returns the trust configuration, including the five trust boundary definitions and the composition rules.

For authenticated verification of a specific tenant's data:

  • Per-nest: GET /api/nests/{id}/verification — checks chain integrity and returns claim-level freshness
  • Per-execution: GET /api/executions/{id}/trace — returns the full event chain with hash verification
  • Tenant-wide: GET /api/tenant/audit/export — exports the complete audit trail for independent verification

To verify independently: re-serialize each event's payload using canonical hashing (JSON keys sorted alphabetically, no whitespace, null values preserved), compute SHA-256, and compare against the stored event_hash. Each hash should include the previous event's hash, forming the chain.

Can Raptor run air-gapped?

Yes. Raptor's runtime dependencies are minimal:

  1. Docker — to run the Raptor container
  2. PostgreSQL 16+ — the governance event store
  3. Network access to at least one AI provider — Raptor needs to reach the provider's API endpoint to generate responses

That is it. Raptor does not phone home, does not require internet access for governance operations, and does not depend on external services for authentication (Clerk is optional — the Founder Key works without it).

For a fully air-gapped deployment:

  • Use the Founder Key (RAPTOR_ACCESS_TOKEN) for authentication instead of Clerk
  • Host PostgreSQL locally
  • Use a provider that can run on your network (e.g., a local model server compatible with the OpenAI API format, or Together AI's on-premises offering)

The governance substrate — classification, policy enforcement, trust boundaries, hash chaining — operates entirely locally. No external calls are made for governance decisions.
