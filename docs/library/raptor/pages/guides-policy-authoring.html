Policy Authoring

Governance policies define what operations are allowed, with what capabilities and budgets. Policies are default-deny, Ed25519-signed, and immutable once stored. This guide covers the full lifecycle: write, validate, sign, activate, simulate, and rollback.

Policy structure

A policy document is JSON with three required fields:

{
  "version": "1.0",
  "default": "deny",
  "rules": [
    {
      "match": { "operation": "chat_execution" },
      "action": "allow",
      "capabilities": ["chat", "read_context"],
      "budget": {
        "max_duration_ms": 30000,
        "max_steps": 10,
        "max_provider_calls": 5,
        "max_artifacts": 3
      }
    },
    {
      "match": { "operation": "artifact_generate" },
      "action": "allow",
      "capabilities": ["artifact_write"],
      "budget": { "max_artifacts": 10 }
    },
    {
      "match": { "operation": "" },
      "action": "deny"
    }
  ]
}

| Field | Required | Description |
|---|---|---|
| version | Yes | Policy format version |
| default | Yes | Must be "deny" — Raptor enforces default-deny |
| rules | Yes | At least one rule |
| rules[].match.operation | Yes | Operation type to match, or "" for wildcard |
| rules[].action | Yes | "allow" or "deny" |
| rules[].capabilities | No | Capabilities granted when rule matches |
| rules[].budget | No | Resource limits for matched operations |
| rules[].required_approvals | No | Number of human approvals before execution |

Rules are evaluated in order. The first match wins. If no rule matches, the default (deny) applies.

1. Validate

Test your policy without storing or signing it:

curl -X POST https://raptor.harpyits.com/api/admin/policies/validate \
  -H "Authorization: Bearer rpt_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "policy_json": "{\"version\":\"1.0\",\"default\":\"deny\",\"rules\":[{\"match\":{\"operation\":\"chat_execution\"},\"action\":\"allow\"}]}"
  }'

A valid policy returns:

{
  "ok": true,
  "valid": true,
  "version": "1.0",
  "default": "deny",
  "rule_count": 1,
  "policy_hash": "sha256:abc123..."
}

Validation checks: version present, default is "deny", at least one rule, every rule has match.operation and action.

2. Sign

Signing creates a cryptographic attestation using Ed25519. The platform signing key is configured server-side (RAPTOR_SIGNING_PRIVATE_KEY). Requires tenant admin role.

curl -X POST https://raptor.harpyits.com/api/admin/policies/sign \
  -H "Authorization: Bearer rpt_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "policy_json": "{\"version\":\"1.0\",\"default\":\"deny\",\"rules\":[{\"match\":{\"operation\":\"chat_execution\"},\"action\":\"allow\"}]}",
    "policy_version": "1.0"
  }'

Response:

{
  "ok": true,
  "policy_id": "uuid",
  "policy_version": "1.0",
  "policy_hash": "sha256:abc123...",
  "signature": "base64-ed25519-signature",
  "signer_key_id": "key-id",
  "status": "signed",
  "note": "Policy is signed but NOT active. Use /api/admin/policies/{id}/activate to activate."
}

Signing is a separate step from activation. A signed policy is inert until explicitly activated. Anti-replay protection rejects duplicate policy content for the same tenant.

3. Activate

curl -X POST https://raptor.harpyits.com/api/admin/policies/{policy_id}/activate \
  -H "Authorization: Bearer rpt_your_key"

Activation verifies the signature again, then creates a new immutable active row. The previous active policy is superseded — policy rows are never updated or deleted.

4. Simulate

Test how a policy would evaluate a specific operation without activating it:

curl -X POST https://raptor.harpyits.com/api/admin/policies/simulate \
  -H "Authorization: Bearer rpt_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "policy_json": "{\"version\":\"1.0\",\"default\":\"deny\",\"rules\":[{\"match\":{\"operation\":\"chat_execution\"},\"action\":\"allow\",\"capabilities\":[\"chat\"]}]}",
    "operation": "chat_execution"
  }'
{
  "ok": true,
  "operation": "chat_execution",
  "simulated": true,
  "decision": "allow",
  "matched_rule": {
    "match": { "operation": "chat_execution" },
    "action": "allow",
    "capabilities": ["chat"]
  }
}

Simulation is a pure dry-run. No grants are issued, no events are recorded, and no side effects occur.

5. Rollback

Revert to the previous signed policy:

curl -X POST https://raptor.harpyits.com/api/admin/policies/rollback \
  -H "Authorization: Bearer rpt_your_key"

Rollback finds the most recent signed policy with different content from the current active policy, verifies its signature, and activates it. Requires at least two distinct policies in the history.

6. View policy history

curl https://raptor.harpyits.com/api/admin/policies \
  -H "Authorization: Bearer rpt_your_key"

Returns all policy versions for the tenant with their status (active, signed, superseded), hash, and signer key ID.

Governance modes

| Mode | Behavior |
|---|---|
| permissive | All known operations allowed (development default) |
| enforced | Only operations explicitly allowed by a signed, verified policy |

Set via the RAPTOR_GOVERNANCE_MODE environment variable. Production defaults to enforced.

In enforced mode, policy management operations (validate, sign, activate, rollback, simulate) are always allowed — they are bootstrap operations that cannot require a policy to manage policies.
