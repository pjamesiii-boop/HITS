Monitoring

Health endpoints, operational metrics, provider monitoring, and integrity verification for Raptor in production.

Monitoring

Raptor exposes structured health, metrics, and integrity endpoints. This guide covers what to monitor, what each endpoint returns, and how to set up alerting.

Health Endpoints

Liveness: /api/health

Returns 200 OK if the control-panel process is running.

curl http://localhost:4000/api/health
{"status": "ok"}

Use this for container orchestration liveness probes. A non-200 response means the process should be restarted.

Readiness: /api/ready

Returns 200 OK if the database is connected and migrations are applied. Returns 503 otherwise.

curl http://localhost:4000/api/ready
{"status": "ready", "database": "connected"}

Use this as your load balancer health check. An instance that fails readiness should be removed from the traffic pool until it recovers.

Dependency Health: /api/health/dependencies

Returns per-dependency status for database, AI providers, and optional integrations.

curl http://localhost:4000/api/health/dependencies
{
  "status": "ok",
  "dependencies": {
    "database": {"status": "ok", "latency_ms": 2},
    "anthropic": {"status": "ok", "latency_ms": 145},
    "openai": {"status": "degraded", "latency_ms": 980}
  }
}

Operational Health Metrics

/api/runtime/health/operational

Returns real-time operational metrics for the running instance.

curl http://localhost:4000/api/runtime/health/operational \
  -H "X-Raptor-Token: your-access-token"

Key fields in the response:

| Field | Description |
|---|---|
| pool_utilization | PostgreSQL connection pool usage (percentage) |
| request_rate | Requests per second over the last 60 seconds |
| error_rate | Error percentage over the last 60 seconds |
| provider_health | Per-provider status and latency |
| uptime_seconds | Time since last process start |

Alert thresholds:

| Metric | Warning | Critical |
|---|---|---|
| Pool utilization | > 70% | > 90% |
| Error rate | > 1% | > 5% |
| Request latency (p95) | > 500 ms | > 1 s |

Provider Monitoring

/api/runtime/config

Returns the active provider configuration (keys are redacted).

curl http://localhost:4000/api/runtime/config \
  -H "X-Raptor-Token: your-access-token"

Use this to verify which providers are configured and which is currently primary. Multi-provider failover is automatic -- Raptor routes to the next healthy provider when the primary fails.

/api/runtime/network

Returns network-level diagnostics: provider reachability, DNS resolution, and TLS status.

curl http://localhost:4000/api/runtime/network \
  -H "X-Raptor-Token: your-access-token"

This endpoint is useful for diagnosing connectivity issues in restricted network environments.

Integrity Monitoring

Integrity monitoring verifies that the running binary matches its build attestation and that the governance hash chain is intact.

/api/runtime/integrity

Returns the current integrity status of the running instance.

curl http://localhost:4000/api/runtime/integrity \
  -H "X-Raptor-Token: your-access-token"
{
  "status": "verified",
  "build_hash": "sha256:abc123...",
  "signer": "ed25519:pubkey...",
  "chain_head": "evt_20260521_00042",
  "chain_valid": true
}

A status of anything other than "verified" requires investigation. See the Integrity Failure Response runbook for procedures.

/api/runtime/integrity/events

Returns recent integrity-related events: attestation checks, chain validations, and any anomalies.

curl http://localhost:4000/api/runtime/integrity/events \
  -H "X-Raptor-Token: your-access-token"

Public Transparency Endpoints

These endpoints are unauthenticated and intended for external verification:

| Endpoint | Purpose |
|---|---|
| /.well-known/raptor/attestation | Ed25519 build attestation (signature, commit hash, build timestamp) |
| /.well-known/raptor/transparency | Hash chain transparency log for independent audit |

Suggested Alerting Configuration

Critical Alerts (page immediately)

  • /api/ready returns non-200 for > 30 seconds
  • /api/runtime/integrity status is not "verified"
  • Error rate exceeds 5% over a 5-minute window
  • Hash chain validation fails (chain_valid: false)

Warning Alerts (notify during business hours)

  • /api/health/dependencies shows any provider as "degraded" for > 5 minutes
  • Pool utilization exceeds 70% sustained over 10 minutes
  • Request latency (p95) exceeds 500 ms over a 5-minute window
  • Integrity event log shows attestation_missing or untrusted_signer

Informational (log and review)

  • Provider failover events (automatic, but worth tracking frequency)
  • Migration events on startup
  • Configuration changes detected via /api/runtime/config

Integration Examples

Prometheus / Grafana

If you expose Raptor metrics to Prometheus, scrape /api/runtime/health/operational at 15-second intervals. Key metric names follow the raptor_ prefix convention.

Uptime Monitors (Pingdom, UptimeRobot, Checkly)

Point your HTTP check at:

GET /api/ready
Expected status: 200
Expected body contains: "ready"
Interval: 30 seconds

PagerDuty / Opsgenie

Route critical alerts (readiness failures, integrity drift) to your on-call rotation. Route warning alerts to a lower-urgency channel.
