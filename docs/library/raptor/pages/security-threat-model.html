Threat Model

Attack surfaces, trust boundaries, and mitigations in Raptor's security architecture.

Threat Model

This document describes the attack surfaces Raptor is designed to resist, the mitigations in place, and the trust assumptions the system makes.

Attack Surfaces

API Endpoint Abuse

Threat: An attacker sends malformed, high-volume, or crafted requests to public API endpoints to exhaust resources, extract data, or bypass governance.

Mitigations:

  • Per-tenant rate limiting enforced at the middleware layer
  • Input validation on all API endpoints before governance processing
  • Structured error responses that do not leak internal state
  • All requests require authentication — there are no anonymous API endpoints except health checks and .well-known public verification endpoints

Authentication Bypass

Threat: An attacker attempts to forge JWTs, steal API keys, or exploit the Founder Key to gain unauthorized access.

Mitigations:

  • JWT: Verified against Clerk's published JWKS on every request. Expired tokens are rejected. Token claims are validated against the tenant binding.
  • API keys: Only SHA-256 hashes are stored. A database breach does not expose usable credentials. Keys are prefixed (rpt_) for easy identification and rotation.
  • Founder Key: Compared using constant-time comparison (SHA-256) to prevent timing attacks. Intended for bootstrap only — should be rotated once Clerk is configured.
  • Grace period: Authentication transitions (e.g., Clerk configuration changes) include a grace period to prevent lockouts, with explicit logging of grace-period authentications.

Provider Compromise

Threat: A compromised or malicious AI provider returns manipulated responses designed to bypass governance, exfiltrate data, or inject harmful content.

Mitigations:

  • Trust boundaries reflect verification status, not provider claims. A provider's response is classified based on what Raptor can verify (Confirmed, Retrieved) versus what it cannot (Likely, Uncertain). Provider self-reported confidence is not trusted.
  • Deterministic governance core. The classification, policy enforcement, and trust boundary assignment layers are deterministic code, not AI. A compromised provider cannot influence governance decisions.
  • Hash chain immutability. Provider responses are recorded in the hash-chained audit log. If a provider's behavior changes or is later found to be compromised, the historical record is intact and verifiable.
  • BYOP model. Customers use their own provider API keys. Raptor does not proxy through a shared credential — a compromise of one customer's provider key does not affect others.

Tenant Isolation Breach

Threat: An attacker with valid credentials for one tenant attempts to access another tenant's data.

Mitigations:

  • PostgreSQL RLS enforced on 30 tables with FORCE ROW LEVEL SECURITY
  • Database-level enforcement means application-layer bugs cannot leak cross-tenant data
  • Tenant ID set at connection level via SET LOCAL — not passed as a query parameter that could be manipulated
  • No shared mutable state between tenants. System configuration tables are read-only from the application role.
  • API keys are tenant-scoped — a key cannot be used to access a different tenant even if the attacker knows the tenant ID.

Hash Chain Tampering

Threat: An attacker with database access attempts to modify, delete, or insert records into the hash-chained audit trail.

Mitigations:

  • Database-level triggers on 11 immutable tables prevent UPDATE and DELETE operations. These triggers fire regardless of the database role executing the query.
  • Chain linking means modifying any single event invalidates all subsequent hashes. Tampering is detectable by any party that can read the chain.
  • Canonical hashing (sorted keys, no whitespace, deterministic serialization) means any independent implementation can verify hashes.
  • Public verification endpoints (/.well-known/raptor/attestation, /.well-known/raptor/transparency) allow external parties to verify chain integrity without requiring database access.

Webhook Interception

Threat: An attacker intercepts or forges webhook payloads to trigger unauthorized actions in a customer's downstream systems.

Mitigations:

  • HMAC-SHA256 signatures on every outbound webhook payload using per-tenant secrets
  • Timestamp headers for replay protection — recipients should reject payloads older than a configured threshold
  • Webhook secrets stored as hashes — a database breach does not expose usable signing keys
  • TLS required for webhook delivery URLs

Trust Boundaries

The Deterministic Core Cannot Be Overridden by AI Output

This is the fundamental trust boundary in Raptor's architecture.

The governance layer — classification, policy enforcement, trust boundary assignment, hash chaining, and authorization — is deterministic code. It does not call AI models. It does not accept AI output as input to governance decisions.

AI is used for exactly one thing: generating response content within the proposal layer. Everything that wraps that content — what the AI is asked, what it is permitted to do, how its output is classified, and what is recorded — is deterministic.

A compromised, hallucinating, or adversarial AI model cannot:

  • Escalate its own permissions
  • Bypass policy enforcement
  • Modify its trust boundary classification
  • Alter the audit trail
  • Access another tenant's data
  • Execute actions without human confirmation (for action types that require it)

Provider Trust Is Earned, Not Assumed

Trust boundaries on AI-generated content reflect what Raptor has actually verified:

  • Confirmed/Executed/Retrieved require evidence from a system of record — not the provider's assertion
  • Likely/Uncertain honestly label content that depends on AI inference
  • The weakest trust boundary in a response dominates the response-level classification

A provider claiming high confidence does not result in a Confirmed trust boundary. Verification against an authoritative source does.

Hash Chain Integrity Is Database-Enforced

The immutability guarantee does not depend on application code behaving correctly.

Database triggers on immutable tables fire on every UPDATE and DELETE attempt and raise an exception. This means:

  • A bug in application code cannot accidentally modify audit records
  • A compromised application server cannot tamper with the chain
  • The only way to bypass the triggers is direct database superuser access with trigger disabling — which is an infrastructure-level attack, not an application-level one

Assumptions

This threat model assumes:

  1. The database hosting provider is trustworthy. Encryption at rest is delegated to the database provider. A compromised hosting provider with raw disk access could read data.
  2. TLS termination is correctly configured. Self-hosted deployments must terminate TLS at a reverse proxy. Raptor does not enforce TLS internally.
  3. Clerk's identity infrastructure is trustworthy. JWT verification depends on Clerk's JWKS endpoint being honest. A compromise of Clerk's signing keys would allow forged JWTs.
  4. Environment variables are protected. The Founder Key, database credentials, and provider API keys are stored as environment variables. If the deployment environment is compromised, these secrets are exposed.

These are standard assumptions for a cloud-native application. They are stated explicitly so that operators can evaluate whether they are acceptable for their threat environment.
