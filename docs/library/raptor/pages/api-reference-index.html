API Reference

Complete REST API documentation for the Raptor governance substrate.

API Reference

The Raptor API is a REST API that provides programmatic access to the governance substrate. Every endpoint returns structured JSON with deterministic trust metadata.

Base URL

| Environment | Base URL |
|-------------|----------|
| Cloud | https://raptor.harpyits.com |
| Self-hosted | http://localhost:4000 |

All paths in this reference are relative to the base URL.

Authentication

Raptor supports three authentication modes. Every endpoint except public well-known routes requires one.

Clerk JWT (Bearer Token)

Used by browser sessions and applications integrated with Clerk identity.

curl -H "Authorization: Bearer eyJhbGciOiJSUzI1NiIs..." \
  https://raptor.harpyits.com/api/nests

The token is a standard Clerk-issued JWT. In browser contexts, it is attached automatically via the session cookie. Server-side integrations should obtain it from Clerk.getToken().

API Key

Used by backend services, CI pipelines, and SDK integrations. Keys carry the rpt_ prefix.

curl -H "X-Raptor-Key: rpt_live_abc123def456" \
  https://raptor.harpyits.com/api/nests

Create API keys through the Control Panel under Settings, or via the /api/keys endpoint. Keys inherit the permissions of the tenant that created them.

Founder Key (Cookie)

Used by the platform founder for administrative operations. Authenticates via POST /api/auth/founder which sets a signed HTTP-only cookie.

# Authenticate (sets cookie)
curl -c cookies.txt -X POST \
  -H "Content-Type: application/json" \
  -d '{"key": "your_founder_key"}' \
  https://raptor.harpyits.com/api/auth/founder


Subsequent requests use the cookie

curl -b cookies.txt https://raptor.harpyits.com/api/admin/policies

API Versioning

All requests should include the X-Raptor-API-Version header. The current version is 2026-05-09.

curl -H "X-Raptor-API-Version: 2026-05-09" \
  -H "X-Raptor-Key: rpt_live_abc123def456" \
  https://raptor.harpyits.com/api/nests

When the header is omitted, the server defaults to the latest stable version. Breaking changes are always gated behind a new version date.

Rate Limiting

Requests are rate-limited per tenant. Current limits:

| Tier | Requests per minute | Burst |
|------|---------------------|-------|
| Free | 60 | 10 |
| Team | 300 | 50 |
| Growth | 1,000 | 100 |

When rate-limited, the API returns HTTP 429 with Retry-After header (seconds).

Error Format

All errors follow a consistent envelope:

{
  "ok": false,
  "error": "validation_error",
  "message": "Request body failed validation.",
  "detail": "Field 'message' is required.",
  "correlation_id": "req_abc123"
}

| Field | Type | Description |
|-------|------|-------------|
| ok | boolean | Always false for errors |
| error | string | Machine-readable error code |
| message | string | Human-readable summary |
| detail | string | Additional context (optional) |
| correlation_id | string | Request trace ID for support (optional) |

Common Error Codes

| HTTP Status | Error Code | Meaning |
|-------------|------------|---------|
| 400 | validation_error | Request body or parameters invalid |
| 401 | unauthorized | Missing or invalid authentication |
| 403 | forbidden | Authenticated but not permitted |
| 403 | governance_denied | Policy blocked the operation |
| 404 | not_found | Resource does not exist |
| 409 | conflict | State conflict (e.g., policy already active) |
| 429 | rate_limited | Too many requests |
| 500 | internal_error | Server error |

Pagination

List endpoints use cursor-based pagination. Pass the after parameter with the ID of the last item from the previous page.

# First page
GET /api/nests


Next page (use the last nest ID from previous response)

GET /api/nests?after=nest_abc123

Paginated responses include:

{
  "ok": true,
  "nests": [...],
  "has_more": true,
  "next_cursor": "nest_abc123"
}

Chat history uses a before cursor for reverse-chronological ordering.

|-------|-------------|-----------|
| Chat | Governed messaging with trust boundaries | Send messages, reset context, retrieve history |
| Nests | Governed conversation containers | Create, list, archive, fork, inspect |

| Policy | Governance policy lifecycle | Validate, sign, activate, rollback, simulate |

| Billing | Stripe-powered billing | Checkout, portal, usage |
| Privacy | GDPR and data governance | Export, delete, consent, retention |
