Compliance Posture

What Raptor implements today for regulatory compliance and what is on the roadmap.

Compliance Posture

This page describes Raptor's compliance capabilities honestly. What is implemented is implemented. What is planned is planned. We do not use aspirational language to describe incomplete work.

Implemented Today

GDPR

Raptor implements structural compliance with the following GDPR articles:

| Article | Requirement | Implementation |
|---------|-------------|----------------|
| Article 6 | Lawful basis for processing | Consent records with explicit grant/revoke tracking, timestamps, IP address, and user agent |
| Article 7 | Conditions for consent | Consent management system with revocation support and full audit trail |
| Article 17 | Right to erasure | Data subject request workflow. Mutable data is deleted. Immutable audit records have PII redacted while hash chain integrity is preserved |
| Article 20 | Data portability | JSON export of all tenant data across 12 tables via API |
| Article 28 | Processor obligations | Tenant isolation enforced at database level via PostgreSQL RLS on 30 tables |

CCPA

| Right | Implementation |
|-------|----------------|
| Right to know | Full data export in JSON format, covering all data associated with the requesting user |
| Right to delete | Data subject request workflow with status tracking and completion timestamps |
| Right to opt-out | Consent records support explicit opt-out with audit trail |

Immutable Audit Trail

Raptor's hash-chained event log satisfies regulatory requirements for tamper-evident record-keeping:

  • Every governed operation is recorded with a cryptographic hash linking it to the previous event
  • 11 tables are protected by database-level triggers that prevent modification or deletion
  • The audit trail can be independently verified by any party using the canonical hashing specification
  • Export endpoints provide the complete chain for external audit tools

This is relevant to any regulation that requires demonstrable record integrity, including SOX, FINRA, and sector-specific audit mandates.

Data Retention Controls

  • Per-tenant retention policies configurable by resource type
  • Configurable retention periods from 30 days to indefinite
  • Optional auto-delete when retention period expires
  • Immutable tables are exempt from deletion — they form the cryptographic chain

Tenant Isolation

  • PostgreSQL Row-Level Security enforced on 30 tables
  • FORCE ROW LEVEL SECURITY applied system-wide — even the database owner role is subject to RLS
  • No cross-tenant data access is possible through application code
  • Tenant-scoped API keys, webhooks, policies, and audit trails

Roadmap

The following capabilities are planned. They are not implemented.

Enterprise tier is not currently available. These capabilities are real preconditions for enterprise deployment, not gating language designed to drive sales conversations.

SOC 2 Type 2

  • Status: Not started
  • Preconditions: Formal control documentation, third-party audit engagement, 6-12 month observation window
  • What exists today: The hash-chained audit trail, RBAC, tenant isolation, and immutability triggers provide the technical controls that a SOC 2 audit would evaluate. The organizational and procedural controls are not yet formalized.

HIPAA Business Associate Agreement

  • Status: Not started
  • Preconditions: BAA legal framework, PHI handling procedures, breach notification process, minimum necessary access controls
  • What exists today: Tenant isolation and audit logging provide the access control and auditability that HIPAA requires. PHI-specific handling (encryption of designated fields, access logging to the individual record level) is not yet implemented.

FedRAMP

  • Status: Not started
  • Preconditions: FedRAMP authorization package, third-party assessment organization (3PAO), agency sponsor
  • What exists today: This is a multi-year effort. Current architecture decisions (tenant isolation, immutable audit, deterministic governance) are compatible with FedRAMP requirements but the authorization process has not begun.

Data Residency

  • Status: Planned
  • Target: US and EU regions
  • Preconditions: Multi-region database deployment, region-aware routing, data classification per tenant
  • What exists today: Single-region deployment. Database hosting region is determined by the deployment provider (Railway, AWS, etc.).

PII Redaction

  • Status: Planned
  • Preconditions: PII detection pipeline, redaction-before-storage for designated fields, redaction-in-place for existing data with hash chain preservation
  • What exists today: Right-to-erasure workflow redacts PII from immutable records while preserving hash integrity. Proactive PII detection and automatic redaction before storage is not yet implemented.

Customer-Managed Encryption Keys (BYOK)

  • Status: Planned
  • Preconditions: Key management integration (AWS KMS, GCP KMS, Azure Key Vault), envelope encryption, key rotation workflow
  • What exists today: Encryption at rest is provided by the database hosting provider. Application-level encryption with customer-managed keys is not implemented.
