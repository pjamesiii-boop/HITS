Operations

Day-to-day operational guidance for monitoring, deploying, backing up, and scaling Raptor.

Operations

This section covers everything you need to keep a Raptor instance healthy in production. The core operational loop is: monitor health, deploy via git push, back up the database, and verify integrity.

Health Monitoring

Raptor exposes three health endpoints out of the box:

| Endpoint | Purpose |
|---|---|
| /api/health | Liveness -- is the process running? |
| /api/ready | Readiness -- is the database connected and are migrations applied? |
| /api/health/dependencies | Per-dependency health breakdown |

Point your uptime monitor at /api/ready. If it returns anything other than {"status": "ready"}, the instance should not receive traffic.

For deeper operational metrics -- connection pool utilization, request rates, error rates, and provider health -- see the Monitoring guide.

Deployment

Raptor deploys via git push only. Direct deploy commands (such as railway up) bypass the build attestation pipeline and break provenance. The correct workflow:

git push origin main

The CI pipeline builds the image, signs it with Ed25519 attestation, and deploys. Migrations run automatically on startup via the migrate container.

For Docker Compose environments:

git pull
docker compose build
docker compose up -d

See the Upgrade guide for versioning, rollback, and breaking-change policy.

Backup and Restore

| Environment | Strategy | RPO |
|---|---|---|
| Self-hosted | Scheduled pg_dump | Depends on schedule (target < 1 hour) |
| Cloud (Neon) | Continuous WAL archiving + hourly snapshots | < 1 hour |

After any restore, verify hash chain integrity and governance table counts before accepting traffic. Immutable governance tables must never be modified in place -- restore from backup only.

Full procedures are in the Backup and Restore guide.

Integrity Verification

Raptor's governance chain is cryptographically verifiable. Two endpoints support external auditing:

| Endpoint | Purpose |
|---|---|
| /.well-known/raptor/attestation | Build attestation (Ed25519 signature, build metadata) |
| /.well-known/raptor/transparency | Public transparency log (hash chain verification) |

The Monitoring guide covers integrity monitoring and alerting for attestation drift.

Scaling Considerations

Raptor is a single Go binary backed by PostgreSQL. Scaling follows standard patterns:

  • Vertical: Increase memory and CPU on the control-panel container. PostgreSQL benefits from more shared_buffers and work_mem.
  • Horizontal: Run multiple control-panel instances behind a load balancer. All instances connect to the same PostgreSQL database. Use /api/ready as the load balancer health check.
  • Connection pooling: Raptor uses pgx with built-in connection pooling. Default pool size is tuned for single-instance use. For multiple instances, either reduce per-instance pool size or add PgBouncer.
  • Database: PostgreSQL 16+ with WAL archiving for point-in-time recovery. For high availability, use a managed PostgreSQL service (Neon, RDS, Cloud SQL) with read replicas.

SLO Targets

| Metric | Target |
|---|---|
| Availability | 99.5% |
| Latency (p50) | < 200 ms |
| Latency (p95) | < 1 s |
| Recovery Point Objective (RPO) | < 1 hour |
| Recovery Time Objective (RTO) | < 15 minutes |
