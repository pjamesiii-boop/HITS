Database

PostgreSQL setup, schema migrations, backup/restore, and data retention for self-hosted Raptor.

Database

Raptor uses PostgreSQL 16+ as its sole data store. In a containerized closed environment, any PostgreSQL 16+ database can be designated via the DATABASE_URL environment variable. The Docker Compose bundle includes a PostgreSQL 16 Alpine container, but you can point Raptor at any compatible instance: managed (Neon, RDS, Cloud SQL, Supabase), self-hosted, or local.

Connection

Set the DATABASE_URL environment variable to a standard PostgreSQL connection string:

DATABASE_URL=postgresql://user:password@host:5432/raptor?sslmode=require

For the bundled Docker Compose setup, this is configured automatically using the POSTGRES_PASSWORD variable.

Connection Pooling

For production deployments with multiple control-panel instances or high concurrency, place a connection pooler (PgBouncer, Supavisor, or your managed provider's built-in pooler) between Raptor and PostgreSQL. Raptor uses standard database/sql connection pooling internally, but an external pooler helps when:

  • Running multiple control-panel replicas
  • Database connections are limited (managed tiers)
  • You need connection-level observability

When using an external pooler, ensure it operates in transaction mode (not session mode) for compatibility with Raptor's query patterns.

Schema Migrations

Migrations run automatically on startup. The Docker Compose bundle includes a dedicated migrate container (using golang-migrate) that:

  1. Waits for PostgreSQL to pass its health check
  2. Applies all pending migrations from the /migrations directory
  3. Exits successfully
  4. Only then does the control-panel container start

Migration files are numbered sequentially (001_enums.up.sql, 002_tables.up.sql, etc.) and are idempotent. The migration tool tracks applied versions in a schema_migrations table.

Running Migrations Manually

If you run Raptor outside Docker Compose, apply migrations before starting the binary:

# Using golang-migrate CLI
migrate -path ./migrations \
  -database "postgresql://raptor:password@localhost:5432/raptor?sslmode=disable" \
  up


Or start the migrate container standalone

docker run --rm \
  -v $(pwd)/migrations:/migrations \
  migrate/migrate:v4.17.0 \
  -path=/migrations \
  -database "postgresql://raptor:password@host:5432/raptor?sslmode=disable" \
  up

Migration Safety

  • Migrations are forward-only in production. Down migrations exist for development but should not be used against production data.
  • Each migration is tested against the full sequence from empty schema to HEAD.
  • The control-panel binary will not start until the migrate container exits successfully (in Docker Compose).

Data Model

Raptor's schema divides into two categories with fundamentally different retention characteristics.

Immutable Tables

Eleven tables are protected by database-level triggers that prevent UPDATE and DELETE operations. These are governance evidence: once a record is written, it cannot be altered or removed. There is no expiration. Records are kept indefinitely.

Immutable tables include:

  • execution_events — every inference execution event
  • governance_decisions — every governance decision and its rationale
  • release_deployments — deployment provenance records
  • build_attestations — signed build attestation evidence
  • transparency_log — append-only transparency log entries
  • authorization_events — authorization audit trail
  • witness_attestations — witness attestation records
  • artifact_audit_log — artifact lifecycle audit records

The immutability triggers raise exceptions at the database level, making them independent of application code:

-- Example: execution_events cannot be updated or deleted
CREATE TRIGGER enforce_event_immutability_update
    BEFORE UPDATE ON execution_events
    FOR EACH ROW
    EXECUTE FUNCTION prevent_event_mutation();

Mutable Tables

All other tables (sessions, cached responses, tenant configuration, etc.) follow standard lifecycle patterns. Retention for mutable data is configurable per tenant.

Data Retention

Immutable Records

Immutable audit tables have no expiration. Records are kept indefinitely. This is by design: governance evidence must be available for the lifetime of the system. Plan storage capacity accordingly.

Mutable Records — Default Retention

| Data Category | Default Retention | Configurable |
|---|---|---|
| Audit logs | 7 years (2555 days) | Yes |
| Execution events | 365 days | Yes |
| Session data | 90 days | Yes |
| Cached responses | 30 days | Yes |

Configurable Retention

Mutable table retention is configurable per tenant. Available retention periods:

  • 30 days
  • 90 days
  • 1 year
  • 2 years
  • 3 years
  • 5 years
  • Indefinite

Retention policies are applied by the maintenance subsystem, which runs cleanup jobs on a periodic schedule. Expired records are soft-deleted first, then purged after a grace period.

Backup and Restore

Backup

Use pg_dump for logical backups:

# From Docker Compose
docker compose exec postgres pg_dump -U raptor raptor > backup.sql


From any PostgreSQL client

pg_dump -h host -U raptor -d raptor > backup.sql


Compressed

pg_dump -h host -U raptor -d raptor -Fc > backup.dump

Restore

# From a SQL backup
psql -h host -U raptor -d raptor < backup.sql


From a compressed backup

pg_restore -h host -U raptor -d raptor backup.dump


Into Docker Compose

docker compose exec -T postgres psql -U raptor raptor < backup.sql

Managed Database PITR

If you use a managed PostgreSQL provider with point-in-time recovery (Neon, RDS, Cloud SQL), use their native PITR capabilities for the fastest recovery:

  • Neon: Built-in PITR with branching. Restore to any point in the retention window.
  • RDS: Automated backups with configurable retention (up to 35 days).
  • Cloud SQL: Automated backups with PITR.

Backup Schedule

For production deployments:

| Strategy | Frequency | Retention |
|---|---|---|
| Full logical backup | Daily | 30 days |
| WAL archiving / PITR | Continuous | 7 days minimum |
| Off-site copy | Weekly | 90 days |

Target RPO (Recovery Point Objective) is under 1 hour. See Production Hardening for the full disaster recovery plan.

Storage Growth

Immutable tables grow monotonically. Estimate growth based on your inference volume:

  • Each execution_event row is approximately 2-4 KB
  • Each governance_decision row is approximately 1-2 KB
  • Transparency log entries are approximately 500 bytes each

For a deployment processing 10,000 inferences per day, expect roughly 30-50 MB/day of immutable data growth, or 10-18 GB/year. Mutable data (sessions, cache) is bounded by retention policy.

Monitor database size:

SELECT pg_size_pretty(pg_database_size('raptor'));

Monitor per-table size:

SELECT relname, pg_size_pretty(pg_total_relation_size(relid))
FROM pg_catalog.pg_statio_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 20;
