Multi-Provider Architecture

How Raptor abstracts AI providers behind a unified interface — provider-agnostic governance with built-in failover.

Multi-Provider Architecture

Raptor is not tied to a single AI provider. A unified Provider interface abstracts Anthropic, OpenAI, Gemini, and Together AI behind a common contract. The governance layer does not care which model produced the response — the same trust boundaries, policies, and audit chain apply regardless.

Supported providers

| Provider | Models | Use case |
|----------|--------|----------|
| Anthropic | Claude family | Primary reasoning and governance |
| OpenAI | GPT family | Alternative reasoning, specialized tasks |
| Gemini | Gemini family | Multi-modal, alternative reasoning |
| Together AI | Open-source models | Cost optimization, specialized inference |

The Provider interface

Every provider implements the same interface:

interface Provider {
  chat(messages: Message[], options: ProviderOptions): Promise<ProviderResponse>
  healthCheck(): Promise<HealthStatus>
  estimateCost(messages: Message[]): CostEstimate
}

This means the governance middleware, commit layer, and trust boundary classifier interact with a single abstraction. Adding a new provider means implementing this interface — no changes to governance logic.

Provider selection

Provider selection is configured at the tenant level:

  • Primary provider — handles all requests by default
  • Fallback provider — activated when the primary is unhealthy or rate-limited
  • Per-operation override — specific operations can target specific providers

The selection is deterministic. There is no AI-driven routing — the tenant configuration specifies which provider handles which operations.

Health monitoring

Each provider connection is monitored:

  • Latency tracking — rolling average response time
  • Error rate — percentage of failed requests over a sliding window
  • Rate limit state — remaining capacity within the provider's rate limits
  • Circuit breaker — provider is marked unhealthy after consecutive failures, with automatic recovery checks

When a provider is marked unhealthy, requests fail over to the configured fallback. The failover event is recorded in the audit trail.

Cost model

Raptor operates as inference pass-through: provider cost plus 10%. There is no markup on governance, audit, or trust boundary features — those are included in the platform.

  • Provider costs are tracked per-request and aggregated per-tenant
  • Budget policies can cap provider spend per operation, per day, or per billing cycle
  • Cost estimates are available before execution via the estimateCost method

Provider-agnostic governance

This is the key architectural point: the governance layer sits between the user and the provider, not inside the provider.

  • Trust boundaries are assigned by the commit layer after the provider responds — the provider does not assign its own trust levels
  • Policies are enforced before the request reaches the provider — the provider does not evaluate authorization
  • The hash chain records the provider's response as-is — the provider does not participate in audit

Switching providers changes the AI that generates proposals. It does not change the governance model, the trust boundary taxonomy, the policy enforcement, or the audit chain. The deterministic core is provider-independent.
