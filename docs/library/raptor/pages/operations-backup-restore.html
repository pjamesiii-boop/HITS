Backup and Restore

Database backup strategies, restore procedures, and post-restore verification for self-hosted and cloud Raptor deployments.

Backup and Restore

Raptor's governance data lives in PostgreSQL. The backup strategy depends on your deployment model. Both paths converge on the same post-restore verification process.

Critical rule: Immutable governance tables (events, attestations, hash chain entries) must never be modified in place. If data is corrupted or missing, restore from backup. Manual edits to immutable tables break the hash chain and invalidate the governance audit trail.

Self-Hosted: pg_dump

Full Backup

pg_dump -h localhost -U raptor -d raptor_db \
  --format=custom \
  --file=raptor_backup_$(date +%Y%m%d_%H%M%S).dump

Use --format=custom for compressed, restorable output. Schedule this via cron to meet your RPO target (recommended: every hour or less).

Example cron entry for hourly backups with 7-day retention:

0     pg_dump -h localhost -U raptor -d raptor_db \
  --format=custom \
  --file=/backups/raptor_$(date +\%Y\%m\%d_\%H\%M\%S).dump \
  && find /backups -name "raptor_.dump" -mtime +7 -delete

Full Restore

# Stop the control-panel to prevent writes during restore
docker compose stop control-panel


Restore from backup

pg_restore -h localhost -U raptor -d raptor_db \
  --clean --if-exists \
  raptor_backup_20260521_120000.dump


Restart services (migrations run automatically)

docker compose up -d

Table-Level Restore

If you need to restore a specific table (for example, to recover a dropped mutable configuration table):

pg_restore -h localhost -U raptor -d raptor_db \
  --table=table_name \
  --clean --if-exists \
  raptor_backup_20260521_120000.dump

Do not use table-level restore on immutable governance tables. Restore the full database instead to preserve referential integrity and hash chain continuity.

Cloud (Neon): Point-in-Time Recovery

Neon provides continuous WAL (Write-Ahead Log) archiving with hourly snapshots. Recovery uses Neon's built-in PITR.

How It Works

  • Continuous WAL archiving: Every transaction is captured in real time.
  • Hourly snapshots: Full-state snapshots every hour for faster recovery.
  • RPO: Typically seconds to minutes (bounded by WAL flush interval).

Recovery Procedure

  1. Open the Neon console and navigate to your project.
  2. Select Branches and click Create Branch.
  3. Choose Point in time and select the recovery target (timestamp or LSN).
  4. Neon creates a new branch with the database state at that point.
  5. Update your DATABASE_URL to point to the new branch.
  6. Redeploy the control-panel.
# After updating DATABASE_URL in your environment
docker compose up -d

Or for Railway: git push triggers redeploy with new env var

Branch Cleanup

After confirming the recovery is good, delete the old branch in the Neon console to avoid billing for unused compute.

Post-Restore Verification

After any restore -- regardless of method -- run these checks before accepting traffic.

1. Hash Chain Integrity

curl http://localhost:4000/api/runtime/integrity \
  -H "X-Raptor-Token: your-access-token"

Verify that chain_valid is true. If the chain is broken, the restore is incomplete or corrupted. Restore again from a known-good backup.

2. Governance Table Counts

Connect to the database and verify row counts against your expected baseline:

SELECT 'events' AS table_name, COUNT() FROM governance_events
UNION ALL
SELECT 'attestations', COUNT() FROM attestations
UNION ALL
SELECT 'policies', COUNT() FROM policies
UNION ALL
SELECT 'tenants', COUNT(*) FROM tenants;

Compare with your last known-good counts. A significant drop indicates a partial restore.

3. Active Policy Verification

curl http://localhost:4000/api/runtime/config \
  -H "X-Raptor-Token: your-access-token"

Confirm the active policy matches what you expect. If the restore rolled back a recent policy change, you may need to re-apply it.

4. Signer Trust Verification

curl http://localhost:4000/api/runtime/integrity \
  -H "X-Raptor-Token: your-access-token"

Confirm the signer field shows your expected Ed25519 public key. An untrusted_signer status after restore means the build attestation does not match the running binary.

5. Health Check

curl http://localhost:4000/api/ready

Only route traffic to the instance after /api/ready returns {"status": "ready"}.

Backup Strategy Recommendations

| Concern | Recommendation |
|---|---|
| RPO target | < 1 hour for production |
| Backup storage | Off-host (S3, GCS, or equivalent). Never store backups only on the database host. |
| Encryption | Encrypt backups at rest. Use gpg or your cloud provider's encryption. |
| Testing | Restore from backup to a staging environment at least monthly. |
| Retention | 7 days minimum for hourly backups. 90 days for daily backups. |
