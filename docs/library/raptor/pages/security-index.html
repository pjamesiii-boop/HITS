Security Architecture

Authentication, authorization, data isolation, cryptographic integrity, and privacy controls in Raptor.

Security Architecture

Raptor's security model is built into the substrate, not bolted on after the fact. Authentication, authorization, data isolation, cryptographic integrity, and privacy controls are structural — they operate at the database and middleware layers, not the application layer alone.

Authentication

Raptor supports three authentication modes. Each serves a different operational context.

Clerk SSO (Production)

For workspace users signing in through the Control Panel UI.

  • OAuth 2.0 via Clerk with Google, GitHub, and Microsoft identity providers
  • JWT verification on every request using Clerk's published JWKS
  • Session tokens include tenant binding — a user's Clerk organization maps to exactly one Raptor tenant
  • Token expiration and refresh handled by Clerk's session management

Required variables: CLERK_SECRET_KEY, CLERK_PUBLISHABLE_KEY, CLERK_DOMAIN

API Keys (Infrastructure)

For programmatic access via the REST API.

  • Keys are prefixed with rpt_ for identification
  • Only the SHA-256 hash is stored in the database — the plaintext key is shown once at creation and never again
  • Each key is scoped to a single tenant and carries an explicit set of permissions
  • Keys can be configured with credit-exhaustion behavior: pause requests or continue with degraded service

Founder Key (Bootstrap)

For initial setup and emergency access before Clerk is configured.

  • Set via RAPTOR_ACCESS_TOKEN environment variable
  • Authenticated using SHA-256 constant-time comparison to prevent timing attacks
  • Grants full access to the tenant — intended for bootstrap, not production operation
  • Should be rotated or disabled once Clerk SSO is configured

Authorization

Role-Based Access Control (RBAC)

Every authenticated user or API key is assigned a role within their tenant. Three roles govern access:

| Role | Purpose |
|------|---------|
| Owner | Full administrative control. Manages billing, team, and governance policies. |
| Admin | Operational management. Configures providers, policies, and integrations. |
| Member | Standard usage. Creates nests, sends messages, views governance data. |

Permissions

10 permissions are mapped to roles via the role_permissions table:

| Permission | Owner | Admin | Member |
|------------|:-----:|:-----:|:------:|
| tenant.manage | Yes | No | No |
| billing.manage | Yes | No | No |
| team.manage | Yes | Yes | No |
| provider.manage | Yes | Yes | No |
| policy.manage | Yes | Yes | No |
| api_key.manage | Yes | Yes | No |
| webhook.manage | Yes | Yes | No |
| nest.create | Yes | Yes | Yes |
| nest.read | Yes | Yes | Yes |
| audit.read | Yes | Yes | Yes |

15+ API endpoints are gated by these permissions. Unauthorized requests return 403 Forbidden with a structured error body identifying the missing permission.

Data Isolation

PostgreSQL Row-Level Security

Every tenant's data is isolated at the database level using PostgreSQL RLS.

  • 30 tables have RLS policies enforced via FORCE ROW LEVEL SECURITY
  • The raptor_app database role sets tenant_id on every connection via SET LOCAL
  • Even the database owner role is subject to RLS — cross-tenant access requires explicit opt-out within a transaction
  • Every query is automatically scoped to the authenticated tenant's tenant_id

This is not application-level filtering. A bug in application code cannot leak data across tenants because the database itself enforces the boundary.

Tenant-Scoped Everything

  • Nests, execution events, governance decisions, policies, API keys, billing records, and audit trails are all keyed to tenant_id
  • No shared tables exist between tenants except system-level configuration
  • Indexes are structured as (tenant_id, ...) to ensure query plans respect isolation

Cryptographic Integrity

Hash-Chained Audit Trail

Every governed operation produces an execution event linked to the previous event via SHA-256 hashing.

  • Canonical hashing: JSON keys sorted alphabetically, no whitespace, deterministic number representation, null values preserved
  • Chain linking: each event's event_hash includes the previous_event_hash
  • Database-level immutability: triggers on 11 tables prevent UPDATE and DELETE operations — this cannot be bypassed by application code
  • Verification endpoints: per-nest, per-execution, and tenant-wide chain verification

Protected tables include: execution_events, build_attestations, transparency_log, authorization_events, governance_policies, and 6 others.

Build Attestation

Every deployment can be signed with Ed25519 keys to prove build provenance.

  • Attestation records are stored in the immutable build_attestations table
  • Public verification available at /.well-known/raptor/attestation
  • Attestations link a specific Git commit to a deployed build

Webhook Signatures

Outbound webhooks are signed with HMAC-SHA256 using per-tenant webhook secrets.

  • Recipients verify the signature header to confirm the payload originated from Raptor
  • Replay protection via timestamp headers
  • Secrets are stored hashed — the plaintext is shown once at creation

Encryption

In Transit

All external communication uses TLS 1.2+ encryption. Self-hosted deployments should terminate TLS at a reverse proxy or load balancer.

At Rest

Database-level encryption at rest is provided by the PostgreSQL hosting provider (Railway, AWS RDS, or equivalent). Raptor does not implement application-level encryption at rest — sensitive fields (API key hashes, webhook secret hashes) are stored as one-way hashes, not encrypted values.

Privacy

GDPR Compliance

Raptor implements the following GDPR provisions:

  • Article 6 (Lawful basis): consent records tracked per user with grant/revoke timestamps, IP address, and user agent
  • Article 7 (Conditions for consent): explicit consent management with revocation support
  • Article 17 (Right to erasure): data subject requests processed via the data_subject_requests table. Mutable data is deleted; immutable audit records have PII redacted while preserving hash chain integrity
  • Article 20 (Data portability): JSON export of all tenant data across 12 tables via GET /api/tenant/audit/export
  • Article 28 (Processor obligations): tenant isolation ensures data processing boundaries are structurally enforced

CCPA Compliance

  • Right to know: full data export available on request
  • Right to delete: data subject request workflow with completion tracking
  • Right to opt-out: consent records support opt-out with timestamp and audit trail

Retention Policies

Tenants configure retention policies per resource type via the retention_policies table:

  • Immutable tables (execution events, attestations, authorization events): retained indefinitely — these form the audit chain and cannot be deleted without breaking cryptographic integrity
  • Mutable tables (conversations, uploads, cache): configurable retention from 30 days to indefinite
  • Auto-delete: optional automatic purge when retention period expires

Consent Management

The consent_records table tracks:

  • Consent type (data processing, analytics, marketing)
  • Grant and revocation timestamps
  • IP address and user agent at time of consent
  • Full audit trail of consent state changes
