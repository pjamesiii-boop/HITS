Runbooks

Step-by-step operational procedures for tenant management, policy rollback, provider failover, integrity incidents, and data recovery.

Runbooks

These runbooks are step-by-step procedures for common operational tasks and incident responses. Each runbook assumes you have operator-level access to the Raptor API and database.

Tenant Provisioning

Create a New Tenant

curl -X POST http://localhost:4000/api/tenants \
  -H "X-Raptor-Token: your-access-token" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme Corp",
    "slug": "acme-corp"
  }'

Save the tenant_id from the response.

Verify Tenant Creation

curl http://localhost:4000/api/tenants/acme-corp \
  -H "X-Raptor-Token: your-access-token"

Confirm the tenant appears with status: "active".

Provision First Policy

Every tenant needs at least one active policy before they can make governed requests.

curl -X POST http://localhost:4000/api/tenants/acme-corp/policies \
  -H "X-Raptor-Token: your-access-token" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Default Policy",
    "rules": {
      "trust_threshold": "likely",
      "require_decision_support": true
    }
  }'

Generate Access Token

curl -X POST http://localhost:4000/api/tenants/acme-corp/tokens \
  -H "X-Raptor-Token: your-access-token" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Production API Key",
    "expires_in": "90d"
  }'

The response includes the token value. This is the only time the full token is returned -- store it securely.

Verification Checklist

  • [ ] Tenant exists and is active
  • [ ] At least one policy is active
  • [ ] Access token is generated and stored securely
  • [ ] Test request succeeds with the new token

Tenant Suspension

Use suspension to immediately block a tenant from making governed requests without deleting their data.

Suspend a Tenant

curl -X POST http://localhost:4000/api/tenants/acme-corp/suspend \
  -H "X-Raptor-Token: your-access-token" \
  -H "Content-Type: application/json" \
  -d '{
    "reason": "Billing delinquent since 2026-05-15"
  }'

The tenant's status changes to "suspended". All API requests using their tokens return 403 Forbidden with a structured error indicating suspension.

Unsuspend a Tenant

curl -X POST http://localhost:4000/api/tenants/acme-corp/unsuspend \
  -H "X-Raptor-Token: your-access-token"

The tenant's status returns to "active" and their tokens resume working immediately.

Verification

curl http://localhost:4000/api/tenants/acme-corp \
  -H "X-Raptor-Token: your-access-token"

Confirm status matches the expected state ("suspended" or "active").

Policy Rollback (Emergency)

Use this procedure when a recently deployed policy is causing incorrect governance behavior and needs to be reverted immediately.

Step 1: Identify the Current and Previous Policy

# List policies for the tenant, ordered by creation date
curl "http://localhost:4000/api/tenants/acme-corp/policies?order=desc" \
  -H "X-Raptor-Token: your-access-token"

Note the policy_id of the current active policy and the previous one you want to roll back to.

Step 2: Activate the Previous Policy

curl -X POST http://localhost:4000/api/tenants/acme-corp/policies/{previous_policy_id}/activate \
  -H "X-Raptor-Token: your-access-token"

This immediately makes the previous policy active. The problematic policy is deactivated but not deleted (governance history is preserved).

Step 3: Verify

# Confirm active policy changed
curl http://localhost:4000/api/tenants/acme-corp/policies/active \
  -H "X-Raptor-Token: your-access-token"


Send a test request to verify governance behavior

curl -X POST http://localhost:4000/api/chat \
  -H "X-Raptor-Token: tenant-access-token" \
  -H "Content-Type: application/json" \
  -d '{"message": "Test message for policy verification"}'

Step 4: Document

Record the rollback in your incident log:

  • When the problematic policy was activated
  • When it was rolled back
  • What behavior it caused
  • How many requests were affected (check governance event counts between the two timestamps)

Provider Failover

Raptor handles multi-provider failover automatically. When the primary AI provider fails (timeout, rate limit, 5xx error), Raptor routes to the next configured provider. This runbook covers manual verification and intervention.

Verify Current Provider Status

curl http://localhost:4000/api/health/dependencies \
  -H "X-Raptor-Token: your-access-token"

Check each provider's status field. Values are "ok", "degraded", or "down".

Verify Failover Is Working

curl http://localhost:4000/api/runtime/config \
  -H "X-Raptor-Token: your-access-token"

The active_provider field shows which provider is currently handling requests. If the primary is down, this should show the failover provider.

Manual Provider Override

If automatic failover is not behaving as expected, you can force a specific provider:

curl -X POST http://localhost:4000/api/runtime/config/provider \
  -H "X-Raptor-Token: your-access-token" \
  -H "Content-Type: application/json" \
  -d '{
    "primary": "openai",
    "reason": "Anthropic API degraded, manual override"
  }'

This override persists until you clear it:

curl -X DELETE http://localhost:4000/api/runtime/config/provider \
  -H "X-Raptor-Token: your-access-token"

After clearing the override, automatic failover resumes.

Integrity Failure Response

Integrity failures indicate that the running binary, its attestation, or the governance hash chain is in a state that cannot be verified. These are high-severity events.

Failure Types

| Status | Meaning | Severity |
|---|---|---|
| attestation_missing | No build attestation found. Binary was deployed without signing. | High |
| untrusted_signer | Attestation exists but the signing key is not in the trust store. | Critical |
| invalid_signature | Attestation signature does not match the binary hash. | Critical |
| chain_broken | Hash chain has a gap or inconsistency. | Critical |

Step 1: Assess

curl http://localhost:4000/api/runtime/integrity \
  -H "X-Raptor-Token: your-access-token"

Note the status, signer, and chain_valid fields.

Step 2: Respond by Failure Type

attestation_missing

The binary was deployed without build attestation. This usually means someone used a direct deploy command instead of the CI pipeline.

Fix: Redeploy via git push through the CI pipeline.

git push origin main

The CI pipeline signs the build with Ed25519. After redeploy, verify integrity returns "verified".

untrusted_signer

The build was signed, but with a key that is not in the configured trust store.

Investigate:

  1. Check who triggered the build (CI logs).
  2. Compare the signer public key in the integrity response against your known signing keys.
  3. If the key is legitimate but new, add it to the trust store via environment configuration.
  4. If the key is unrecognized, treat this as a security incident. Do not accept traffic from this instance.

invalid_signature

The attestation signature does not match the binary. The binary may have been modified after signing.

Respond:

  1. Immediately remove the instance from the load balancer.
  2. Do not attempt to fix in place. Redeploy from a known-good image via git push.
  3. Investigate how the binary was modified (check container runtime, host access logs).

chain_broken

The governance hash chain has a gap or inconsistency.

Respond:

  1. Check /api/runtime/integrity/events for details on where the chain breaks.
  2. This typically indicates database corruption or an incomplete restore. See Data Recovery below.
  3. Do not attempt to repair the chain manually. Restore from the last backup where the chain was intact.

Step 3: Verify Resolution

After applying the fix:

curl http://localhost:4000/api/runtime/integrity \
  -H "X-Raptor-Token: your-access-token"

Confirm "status": "verified" and "chain_valid": true before routing traffic.

Data Recovery

Use this procedure when data loss or corruption is detected. The approach depends on severity.

Assess the Damage

-- Check governance event counts
SELECT COUNT(*) FROM governance_events;


-- Check for hash chain gaps
SELECT event_id, previous_hash
FROM governance_events
WHERE previous_hash IS NULL
  AND event_id != (SELECT MIN(event_id) FROM governance_events);

Any rows returned by the second query indicate chain breaks.

Recovery via PITR (Preferred)

For Neon or any PostgreSQL with WAL archiving:

  1. Identify the last known-good timestamp (before corruption occurred).
  2. Create a PITR branch or restore to that timestamp.
  3. Update DATABASE_URL to point to the recovered database.
  4. Redeploy the control-panel.
  5. Run the Post-Restore Verification checklist.

Recovery via pg_restore

For self-hosted without WAL archiving:

docker compose stop control-panel


pg_restore -h localhost -U raptor -d raptor_db \
  --clean --if-exists \
  raptor_backup_YYYYMMDD_HHMMSS.dump



docker compose up -d

What NOT to Do

  • Do not manually insert, update, or delete rows in immutable governance tables (governance_events, attestations, hash_chain). Manual modification invalidates the cryptographic chain and is unrecoverable.
  • Do not attempt to "patch" a broken hash chain by recalculating hashes. The chain must be restored from a backup where it was intact.
  • Do not skip post-restore verification. An incomplete restore that passes health checks but has a broken chain will produce unverifiable governance records going forward.
