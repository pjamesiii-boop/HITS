Proposal/Commit Architecture

Why Raptor separates AI proposals from deterministic commits — and why that separation is the safety model.

Proposal/Commit Architecture

Raptor enforces a hard separation between what AI proposes and what the system commits. AI is never directly connected to execution. This is not a design preference — it is the safety architecture.

The separation

Three layers handle three concerns:

| Layer | Responsibility | Deterministic? |
|-------|---------------|----------------|
| Proposal | AI generates language, recommendations, action suggestions | No — AI is probabilistic |
| Governance | Classify intent, enforce policies, check authorization | Yes — rule evaluation |
| Commit | Structure output, assign trust boundaries, hash-chain, execute | Yes — deterministic core |

The AI layer never touches execution directly. A proposed action passes through governance evaluation and human confirmation before the commit layer executes it.

How a proposed action flows

  1. User says: "Deploy the canary build"
  2. Classifier categorizes intent as propose_action
  3. AI generates a structured proposal:
   {
     "action": "deploy_canary",
     "parameters": { "build_id": "b-4a91", "target": "staging" },
     "reasoning": "Build passed all gates. Canary deploy is next step."
   }
  1. Governance checks: does the policy allow deploy_canary? Is the user authorized? Is the budget within limits?
  2. Proposal is presented to the user with decision support metadata
  3. User confirms
  4. Classifier re-categorizes as execute_confirmed_action
  5. Commit layer executes the action and records the result to the hash chain

If the user does not confirm, the action is never executed. The proposal remains in the audit trail as a proposed-but-not-confirmed event.

What this prevents

Prompt injection leading to execution. Even if an attacker manipulates the AI into proposing a harmful action, the governance layer evaluates the proposal against policies, and the human confirmation gate blocks unauthorized execution.

AI hallucination reaching operations. The AI might hallucinate a capability or a parameter. The commit layer validates the action against the registered action schema before execution. Invalid actions fail at commit, not at runtime.

Unaudited side effects. Every execution passes through the commit layer, which records input, output, timing, and trust classification. There is no path from AI to side effect that bypasses the audit chain.

Conversational responses

Not every response involves an action. For respond and ask intents, the proposal/commit separation still applies:

  • AI generates the conversational content (proposal)
  • Commit layer assigns trust boundaries to each segment
  • Commit layer hashes and chains the output
  • No confirmation gate because there is no side effect

The governance model applies uniformly. The confirmation gate activates only when the classified intent involves execution.

The design principle

AI is good at language. It is not good at authorization, auditability, or deterministic execution. Raptor uses AI for what it is good at and uses deterministic systems for everything else. The proposal/commit boundary is where that division is enforced.
