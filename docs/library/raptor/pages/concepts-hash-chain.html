Hash Chain

How Raptor's immutable audit chain ensures every output is traceable and tamper-evident.

Hash Chain

Every governed operation in Raptor produces an execution event that is linked to the previous event via cryptographic hashing. This creates a tamper-evident chain — if any event is modified after the fact, the chain breaks.

How it works

  1. Every chat turn, action execution, and governance decision creates an execution_event
  2. Each event contains a payload (the full structured output) that is canonically hashed (SHA-256, deterministic JSON serialization, sorted keys)
  3. Each event's event_hash includes the previous_event_hash, creating a linked chain
  4. Database triggers prevent UPDATE and DELETE on the execution_events table

Verification

  • Per-nest: GET /api/nests/{id}/verification checks chain integrity and returns claim-level freshness
  • Per-execution: GET /api/executions/{id}/trace returns the full event chain with hash verification
  • Tenant-wide: GET /api/tenant/audit/export exports the complete audit trail

Immutability guarantees

11 tables in Raptor are protected by database-level triggers that prevent modification:

  • execution_events — the primary hash chain
  • build_attestations — Ed25519 signed build proofs
  • transparency_log — public transparency records
  • authorization_events — governance decision audit trail
  • governance_policies — append-only policy lifecycle

This is not application-level protection — it's database-level enforcement that cannot be bypassed by application code.

Canonical hashing

Raptor uses canonical hashing to ensure identical inputs always produce identical hashes:

  1. JSON keys are sorted alphabetically
  2. No whitespace in serialized form
  3. Numbers use their canonical JSON representation
  4. Null values are preserved (not omitted)

This means any system can independently verify a hash by re-serializing the payload with the same rules.
