Upgrades

Versioning, upgrade procedures, rollback, and API compatibility for Raptor.

Upgrades

Raptor uses date-based versioning and automatic migrations. Upgrades are designed to be low-risk: pull the new image, restart, and verify health.

Versioning

Raptor versions follow a date-based scheme: YYYY-MM-DD (for example, 2026-05-09). Each version corresponds to a tagged release and a container image.

  • Patch releases (same date, incremented suffix like 2026-05-09.1) contain bug fixes only.
  • Minor releases (new date) may add features, endpoints, or configuration options. Existing behavior does not change.
  • Breaking releases are rare and announced in advance. See Breaking Changes Policy below.

Upgrade Procedure

Docker Compose

# Pull the latest code
git pull origin main


Rebuild images

docker compose build


Restart services (migrations run automatically)

docker compose up -d

Railway

Deploy via git push. Railway rebuilds the image and restarts the service automatically.

git push origin main

Do not use railway up or equivalent direct-deploy commands. They bypass build attestation and break provenance.

Verify After Upgrade

# Check readiness
curl http://localhost:4000/api/ready


Check integrity (build attestation matches new version)

curl http://localhost:4000/api/runtime/integrity \
  -H "X-Raptor-Token: your-access-token"


Check dependency health

curl http://localhost:4000/api/health/dependencies

Confirm:

  • /api/ready returns {"status": "ready"}
  • /api/runtime/integrity shows "status": "verified" with the new build hash
  • All dependencies are healthy

Automatic Migrations

The migrate container in Docker Compose runs before the control-panel starts. It applies any pending schema migrations and exits. You do not need to run migrations manually.

If a migration fails, the control-panel will not start. Check the migrate container logs:

docker compose logs migrate

Fix the underlying issue (usually a database connection problem or permission error) and restart:

docker compose up -d

Rollback

If an upgrade causes problems, roll back by restoring the previous database state and redeploying the prior image version.

Step 1: Restore the Database

Point DATABASE_URL at your pre-upgrade backup:

  • Self-hosted: Restore using pg_restore from your most recent pre-upgrade backup. See Backup and Restore.
  • Cloud (Neon): Create a PITR branch targeting a timestamp before the upgrade.

Step 2: Redeploy the Previous Image

# Check out the previous release tag
git checkout 2026-05-09


Rebuild and restart

docker compose build
docker compose up -d

For Railway, push the previous tag to trigger a rebuild:

git push origin 2026-05-09:main --force-with-lease

Step 3: Verify

Run the same post-upgrade verification checks. Confirm health, integrity, and dependency status before routing traffic.

API Version Header

Raptor supports the X-Raptor-API-Version request header for forward compatibility. When a new API version introduces changes to response structure, you can pin your client to a specific version:

curl http://localhost:4000/api/chat \
  -H "X-Raptor-Token: your-access-token" \
  -H "X-Raptor-API-Version: 2026-05-09" \
  -H "Content-Type: application/json" \
  -d '{"message": "Hello"}'

If the header is omitted, the server uses the latest API version. Pinning is recommended for production integrations to avoid unexpected changes during upgrades.

Breaking Changes Policy

Raptor follows these rules for breaking changes:

  1. Advance notice. Breaking changes are announced at least 30 days before they take effect. Announcements appear in the changelog and are sent to the operator email on file.
  2. Version header grace period. When a breaking change ships, the previous API version remains supported for at least 90 days via the X-Raptor-API-Version header.
  3. Migration path. Every breaking change includes documentation for how to update client code.
  4. No silent breaks. If a field is removed or renamed, the old field returns a deprecation warning in the response headers (X-Raptor-Deprecated) before removal.

What Counts as Breaking

  • Removing or renaming a response field
  • Changing the type of a response field
  • Removing an endpoint
  • Changing authentication requirements

What Does Not Count as Breaking

  • Adding new response fields
  • Adding new endpoints
  • Adding new optional request parameters
  • Performance improvements
  • Bug fixes that correct behavior to match documentation
