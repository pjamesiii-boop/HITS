Multi-Tenant Isolation

How Raptor enforces tenant boundaries — row-level security, scoped resources, and the guarantee that data never crosses organizations.

Multi-Tenant Isolation

Every Raptor account maps to one organization. Tenant isolation is enforced at the database level, not the application level. Data never crosses tenant boundaries.

Row-level security

Every table that holds tenant data includes a tenant_id column. PostgreSQL row-level security (RLS) policies ensure that queries can only access rows belonging to the authenticated tenant.

This is not application-level filtering (a WHERE clause that could be forgotten). RLS is enforced by the database engine itself. Even if application code contains a bug that omits the tenant filter, the database rejects the query.

CREATE POLICY tenant_isolation ON execution_events
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

Every API request sets the tenant context before executing any query. The database enforces the boundary from that point forward.

Tenant-scoped resources

The following resources are scoped to a single tenant and cannot be accessed across boundaries:

| Resource | Scope |
|----------|-------|
| Nests | Conversations, memory, governance state |
| Execution events | The complete hash-chained audit trail |
| Governance policies | Active and historical policy versions |
| API keys | Authentication credentials |
| Webhooks | Event notification endpoints |
| Artifacts | Files, documents, generated outputs |
| Billing | Usage tracking, provider costs, invoices |
| RBAC assignments | Role and permission grants |

Identity mapping

Raptor uses Clerk for authentication and organization management. Each Clerk organization maps to exactly one Raptor tenant:

  • Clerk handles user authentication, SSO, and session management
  • Raptor maps the Clerk organization ID to a tenant_id
  • Users belong to a Clerk organization and inherit the corresponding tenant context
  • A user in multiple Clerk organizations accesses each as a separate Raptor tenant

Identity is externalized. Governance is internal. Raptor never stores passwords or manages authentication flows directly.

RBAC within tenant

Each tenant has three roles with 10 permissions:

| Role | Capabilities |
|------|-------------|
| Owner | Full control — policies, billing, member management, all operations |
| Admin | Policy management, member management, all operational permissions |
| Member | Operational use — chat, actions, file access, read governance events |

Permissions are evaluated per-request by the governance middleware. Role assignments are tenant-scoped and recorded in the audit trail.

Tenant suspension

A tenant can be suspended (billing failure, policy violation, administrative action). Suspended tenants:

  • Cannot execute any governed operations
  • Cannot create or modify nests
  • Cannot invoke provider calls
  • Retain read access to existing audit trails and governance history

Suspension is immediate and enforced at the governance middleware layer. Reactivation restores full access. Both events are recorded in the hash chain.

The guarantee

No query, API call, webhook, or background job can access data belonging to another tenant. This is enforced by the database, verified by the governance layer, and auditable through the hash chain.
