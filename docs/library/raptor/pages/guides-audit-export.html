Audit and Compliance

Every governed operation in Raptor produces an immutable, hash-chained record. This guide covers exporting audit data, verifying chain integrity, understanding retention, and implementing regulatory compliance patterns.

1. Export the audit trail

The tenant-wide export endpoint returns four tables of governance evidence:

curl -H "Authorization: Bearer rpt_your_key" \
  https://raptor.harpyits.com/api/tenant/audit/export
{
  "ok": true,
  "tenant_id": "uuid",
  "export": {
    "authorization_events": [...],
    "capability_grants": [...],
    "governance_policies": [...],
    "tenant_events": [...]
  },
  "counts": {
    "authorization_events": 142,
    "capability_grants": 89,
    "governance_policies": 3,
    "tenant_events": 12
  },
  "exported_at": "2026-05-21T14:30:00Z"
}

Authorization events

Each authorization event records a governance decision:

{
  "id": "uuid",
  "operation": "chat_execution",
  "decision": "allowed",
  "reason": "policy_rule_matched",
  "policy_mode": "enforced",
  "correlation_id": "uuid",
  "created_at": "2026-05-21T14:30:00Z"
}

Capability grants

Each grant records what capabilities were issued for an allowed operation, with a cryptographic hash:

{
  "id": "uuid",
  "operation": "chat_execution",
  "capabilities": "chat,read_context",
  "required_approvals": 0,
  "grant_hash": "sha256:abc123...",
  "created_at": "2026-05-21T14:30:00Z"
}

Paginated access

For large audit histories, use the paginated events endpoint:

curl -H "Authorization: Bearer rpt_your_key" \
  "https://raptor.harpyits.com/api/tenant/audit/events?after=cursor_id"

2. Understand the hash chain

Every execution event is linked to the previous event via SHA-256 hashing:

Event N:
  event_hash = SHA-256(payload + previous_event_hash)
  previous_event_hash = Event N-1's event_hash


Event N-1:
  event_hash = SHA-256(payload + previous_event_hash)
  previous_event_hash = Event N-2's event_hash

The payload is canonically serialized (sorted keys, no whitespace, nulls preserved) before hashing. Any system can independently verify a hash by re-serializing with the same rules.

The hash chain is per-tenant, per-nest. Each nest maintains its own chain.

3. Verify chain integrity

Per-nest verification

curl -H "Authorization: Bearer rpt_your_key" \
  https://raptor.harpyits.com/api/nests/{nestId}/verification

Returns chain integrity status and claim-level freshness for the nest.

Per-execution trace

curl -H "Authorization: Bearer rpt_your_key" \
  https://raptor.harpyits.com/api/executions/{id}/trace

Returns the full event chain for a single execution with hash verification at each link.

Independent verification

To verify the chain externally:

  1. Export the execution events for a nest
  2. For each event, canonically serialize the payload (sort keys, no whitespace)
  3. Compute SHA-256(serialized_payload + previous_event_hash)
  4. Compare against the stored event_hash
  5. If any hash mismatches, the chain has been tampered with

4. Immutability guarantees

Raptor's audit tables are protected by database-level triggers that prevent UPDATE and DELETE:

  • execution_events — the primary hash chain
  • authorization_events — governance decision ledger
  • governance_policies — append-only policy lifecycle
  • build_attestations — Ed25519 signed build proofs
  • transparency_log — public transparency records

This is database-level enforcement, not application-level. Application code cannot bypass these triggers.

5. Retention

The audit export endpoint returns the most recent records per table (200 authorization events, 200 capability grants, 50 governance policies, 50 tenant events). For complete historical data, use the paginated events endpoint.

Raptor does not automatically delete audit records. The hash chain is append-only by design — deletion would break chain integrity.

6. GDPR data export

The privacy endpoints support per-user data export:

# Export all data for a specific user
curl -H "Authorization: Bearer rpt_your_key" \
  https://raptor.harpyits.com/api/privacy/export

This returns all governed interactions, governance decisions, and execution artifacts associated with the requesting identity.

7. Regulatory compliance patterns

SOC 2 evidence

The audit export provides the evidence trail SOC 2 auditors need:

  • Every operation authorized with recorded decision and reason
  • Every capability grant with cryptographic hash
  • Policy version history with Ed25519 signatures
  • Tamper-evident chain with independent verifiability

Audit log forwarding

Use webhooks to forward governance events to your SIEM or compliance platform in real time:

curl -X POST https://raptor.harpyits.com/api/webhooks \
  -H "Authorization: Bearer rpt_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://your-siem.com/ingest/raptor",
    "events": ["governance.allowed", "governance.denied", "policy.activated"]
  }'

Chain-of-custody documentation

For each governed response, you can reconstruct the full chain of custody:

  1. Authorization — who requested what, and what policy allowed it
  2. Capability grant — what capabilities were issued, with what budget
  3. Execution — what happened, with trust boundary and segments
  4. Attestation — Ed25519 signed execution receipt

All four are hash-linked and independently verifiable.
