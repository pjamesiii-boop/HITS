Providers

Configure AI providers, failover behavior, and understand inference pricing in Raptor.

AI Providers

Raptor acts as a governance layer between your application and AI providers. It does not host models. You supply provider API keys, and Raptor routes inference requests through its governance engine before forwarding them to the provider.

Supported Providers

| Provider | Environment Variable | Models |
|---|---|---|
| Anthropic | ANTHROPIC_API_KEY | Claude 4 Opus, Claude 4 Sonnet, Claude 3.5 family |
| OpenAI | OPENAI_API_KEY | GPT-4o, GPT-4o-mini, o1, o3 family |
| Google | GEMINI_API_KEY | Gemini 2.5 Pro, Gemini 2.5 Flash family |
| Together AI | TOGETHER_API_KEY | Llama, Mixtral, open-weight models |

At least one provider key is required. Set the corresponding environment variable and Raptor detects the provider at startup.

Configuration

Add provider keys to your .env file:

# Set one or more
ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-...
GEMINI_API_KEY=AIza...
TOGETHER_API_KEY=...

Restart the control-panel after changing provider keys:

docker compose restart control-panel

Verifying Provider Status

Check which providers are active and healthy:

curl http://localhost:4000/api/runtime/config

The response includes the list of configured providers and their status. Use this endpoint for monitoring dashboards and alerting.

Multi-Provider Failover

When multiple providers are configured, Raptor provides automatic failover:

  1. Primary routing: Requests specify a model (e.g., claude-sonnet-4-20250514). Raptor routes to the corresponding provider.
  2. Provider failure: If the primary provider returns a 5xx error or times out, Raptor can fall back to an equivalent model on another configured provider.
  3. Health tracking: Provider health is tracked at the connection level. Unhealthy providers are deprioritized until they recover.

Failover is transparent to the calling application. The governance decision records which provider ultimately served the request.

Provider Health Monitoring

Monitor provider health through the dependency health endpoint:

curl http://localhost:4000/api/health/dependencies

This reports the status of each configured provider alongside database connectivity and other dependencies. Wire this into your monitoring system to detect provider outages before they impact users.

Pricing

Inference Pass-Through

When Raptor manages provider keys (operator-supplied keys), inference is billed at pass-through pricing:

Provider cost + 10% governance fee

The provider cost is the standard rate from the provider (Anthropic, OpenAI, etc.) for the model and token volume used. The 10% governance fee covers the governance engine, audit trail, and platform infrastructure.

BYOP (Bring Your Own Provider)

Customers can use their own provider API keys instead of operator-managed keys. In the BYOP model:

  • The customer pays the provider directly at their negotiated rate
  • Raptor charges a flat $0.012 governance fee per request
  • No percentage markup on inference cost

BYOP is ideal for customers with:

  • Negotiated enterprise pricing with providers
  • High-volume workloads where the flat fee is more economical
  • Compliance requirements that mandate direct provider relationships

Pricing Summary

| Model | Provider Cost | Raptor Fee |
|---|---|---|
| Operator-managed keys | Pass-through | +10% of provider cost |
| BYOP (customer keys) | Paid directly by customer | $0.012 per request |

Provider Policies

Raptor's governance engine can enforce provider-level policies:

  • Allowed providers: Restrict which providers a tenant can use
  • Model restrictions: Limit which models are available
  • Rate limits: Per-provider rate limiting at the tenant level
  • Cost caps: Maximum spend per provider per billing period

Provider policies are configured through the Control Panel UI or the governance API. Policy changes are recorded in the immutable audit trail.
