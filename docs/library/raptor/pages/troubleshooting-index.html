Troubleshooting

Common issues, their causes, and how to fix them.

Troubleshooting

This guide covers the most common issues you will encounter when running Raptor, organized by category. Each issue includes the symptom, likely cause, and fix steps.

Authentication

401 Unauthorized — Expired JWT

Symptom: API requests return 401 with "error": "token_expired".

Cause: The Clerk session token has expired and the client has not refreshed it.

Fix:

  1. If using the Control Panel UI, sign out and sign back in.
  2. If using a custom client, ensure your Clerk SDK is configured to refresh tokens automatically.
  3. Check that your server's clock is synchronized (NTP). JWT validation is time-sensitive.

401 Unauthorized — Missing API Key

Symptom: API requests return 401 with "error": "missing_credentials".

Cause: The request does not include an authentication header.

Fix:

  1. For API key authentication, include the header: Authorization: Bearer rpt_your_key
  2. For Founder Key authentication, include the header: X-Raptor-Token: your_access_token
  3. Verify the key exists and has not been revoked in Settings > API Keys.

401 Unauthorized — Clerk Misconfiguration

Symptom: All Clerk-authenticated requests return 401. API key requests work fine.

Cause: Clerk environment variables are missing or incorrect.

Fix:

  1. Verify these environment variables are set:
- CLERK_SECRET_KEY — starts with sk_live_ or sk_test_ - CLERK_PUBLISHABLE_KEY — starts with pk_live_ or pk_test_ - CLERK_DOMAIN — your Clerk domain (e.g., your-app.clerk.accounts.dev)
  1. Ensure the Clerk application's JWT template matches Raptor's expected claims.
  2. Restart the Raptor process after changing environment variables.

401 Unauthorized — Grace Period

Symptom: Requests return 401 intermittently during an authentication configuration change.

Cause: Raptor includes a grace period during authentication transitions. If you are seeing 401 errors during this window, the new configuration may be invalid.

Fix:

  1. Check the application logs for grace-period authentication entries — these indicate which authentication method was attempted and why it failed.
  2. Verify the new authentication configuration is correct before the grace period expires.
  3. If locked out, use the Founder Key (X-Raptor-Token) to regain access.

403 Forbidden — Permission Denied

Symptom: API requests return 403 with "error": "permission_denied" and a "required_permission" field.

Cause: The authenticated user or API key does not have the required permission for this endpoint.

Fix:

  1. Check the required_permission field in the error response (e.g., "provider.manage").
  2. Verify the user's role in Settings > Team. Permissions are mapped to roles: Owner, Admin, Member.
  3. If using an API key, check the key's assigned permissions in Settings > API Keys.
  4. See the permission matrix for which roles grant which permissions.

403 Forbidden — Tenant Suspended

Symptom: All requests return 403 with "error": "tenant_suspended".

Cause: The tenant has been suspended, typically due to billing issues or policy violations.

Fix:

  1. Check your billing status in Settings > Billing.
  2. If billing is current, contact support with your tenant ID.

Provider

503 Service Unavailable — No Provider Configured

Symptom: Chat requests return 503 with "error": "no_provider_available".

Cause: No AI provider API key has been configured for this tenant.

Fix:

  1. Go to Settings > Providers and add at least one provider API key.
  2. Supported providers: Anthropic (ANTHROPIC_API_KEY), OpenAI (OPENAI_API_KEY), Google Gemini (GEMINI_API_KEY), Together AI (TOGETHER_API_KEY).
  3. For self-hosted deployments, set the provider key as an environment variable and restart.

Slow Responses

Symptom: Chat requests take 10+ seconds to return.

Cause: Provider latency. Raptor adds minimal overhead (governance processing is typically under 50ms). Slow responses are almost always due to the upstream AI provider.

Fix:

  1. Check your provider's status page for ongoing incidents.
  2. Try a different provider if you have multiple configured.
  3. For self-hosted deployments, verify network connectivity to the provider's API endpoint.
  4. Check if your provider account has been rate-limited or throttled.

Provider Errors — Quota Exceeded

Symptom: Chat requests return an error with "provider_error": "rate_limit_exceeded" or "quota_exceeded".

Cause: Your provider API key has exceeded its usage limits.

Fix:

  1. Check your provider dashboard for current usage and limits.
  2. Upgrade your provider plan if you have hit a spending cap.
  3. Configure multiple providers in Raptor for automatic failover.

Provider Errors — Invalid Key

Symptom: Chat requests return an error with "provider_error": "authentication_failed".

Cause: The provider API key is invalid, expired, or revoked.

Fix:

  1. Verify the API key in your provider's dashboard.
  2. Generate a new key if the current one has been revoked.
  3. Update the key in Settings > Providers (cloud) or the environment variable (self-hosted).

Database

Connection Failures

Symptom: Raptor fails to start with "error": "database_connection_failed" or requests return 500 errors.

Cause: The PostgreSQL database is unreachable.

Fix:

  1. Verify DATABASE_URL is set correctly. Format: postgresql://user:password@host:port/database
  2. Confirm the database server is running and accepting connections.
  3. Check firewall rules — the Raptor process must be able to reach the database host and port.
  4. For Docker deployments, ensure the database container is healthy: docker compose ps

Migration Errors

Symptom: Raptor fails to start with a migration error referencing a specific migration number.

Cause: A database migration failed to apply, often due to a schema conflict or interrupted previous migration.

Fix:

  1. Check the migration error message for the specific failure.
  2. Verify the database user has CREATE TABLE, ALTER TABLE, and CREATE TRIGGER permissions.
  3. If a migration was interrupted, check the schema_migrations table for a dirty state.
  4. For self-hosted deployments, ensure you are running the version of Raptor that matches your database schema.

Pool Exhaustion

Symptom: Intermittent 500 errors with "error": "pool_exhausted" or "connection_timeout".

Cause: All database connections in the pool are in use.

Fix:

  1. Check for long-running queries: SELECT * FROM pg_stat_activity WHERE state = 'active' ORDER BY query_start;
  2. Increase the connection pool size if your workload requires it.
  3. Verify that no external process is holding connections open against the same database.

Hash Chain

Integrity Verification Failure

Symptom: GET /api/nests/{id}/verification returns "chain_valid": false.

Cause: A hash in the chain does not match the expected value. This indicates either data corruption or tampering.

Fix:

  1. This is a serious condition. Do not ignore it.
  2. Identify the specific event where the chain breaks — the verification response includes the break_point event ID.
  3. Compare the stored event_hash against a recomputed hash of the payload using Raptor's canonical hashing rules (sorted keys, no whitespace, deterministic serialization).
  4. If the mismatch is due to a known schema migration, check the migration notes for hash recomputation instructions.
  5. If tampering is suspected, export the full chain via GET /api/tenant/audit/export and preserve it for forensic analysis.

Attestation Missing

Symptom: GET /.well-known/raptor/attestation returns 404 or an empty response.

Cause: No build attestation has been recorded for the current deployment.

Fix:

  1. Build attestations are created during the deployment process. If you built from source without the attestation step, no attestation exists.
  2. For Docker deployments, verify the image was built from a tagged release that includes attestation.
  3. A missing attestation does not affect governance functionality — it means the build provenance cannot be independently verified.

Deployment

Docker Health Check Failures

Symptom: docker compose ps shows the Raptor container as unhealthy.

Cause: The health check endpoint (/api/health) is not responding.

Fix:

  1. Check container logs: docker compose logs raptor
  2. Verify the CONTROL_HOST is set to 0.0.0.0 (not localhost) for containerized deployments.
  3. Verify the CONTROL_PORT matches the port exposed in your Docker Compose file.
  4. Ensure the database is reachable from the container — the health check verifies database connectivity.

Port Conflicts

Symptom: Raptor fails to start with EADDRINUSE or similar port-binding error.

Cause: Another process is already using the configured port.

Fix:

  1. Check what is using the port: lsof -i :4000 (or your configured port).
  2. Change the port via CONTROL_PORT environment variable.
  3. For Docker deployments, change the host port mapping in your Docker Compose file.

Environment Variable Misconfiguration

Symptom: Raptor starts but specific features do not work (e.g., Clerk auth, billing, providers).

Cause: One or more environment variables are missing or incorrect.

Fix:

  1. Required variables for basic operation:
- DATABASE_URL — PostgreSQL connection string - RAPTOR_ACCESS_TOKEN — Founder Key for bootstrap authentication - At least one provider key (ANTHROPIC_API_KEY, OPENAI_API_KEY, etc.)
  1. Check the environment variables reference for the full list.
  2. For Docker deployments, ensure variables are set in your .env file or Docker Compose environment section.
  3. Restart the Raptor process after any environment variable change.
