Production Hardening

TLS, authentication, monitoring, disaster recovery, and scaling for production Raptor deployments.

Production Hardening

This guide covers everything required to run Raptor in production. Work through each section before exposing the deployment to real traffic.

Environment

Set RAPTOR_ENV=production. This enables:

  • Strict authentication enforcement
  • Reduced error verbosity in API responses
  • Production-appropriate logging levels
  • Security headers on all responses

TLS Termination

Raptor listens on plain HTTP. Terminate TLS at a reverse proxy or load balancer in front of the control-panel and MCP server.

Recommended Setup

Internet ──► TLS termination (nginx / Caddy / ALB) ──► Raptor :4000
                                                   ──► MCP    :4001

Nginx example:

server {
    listen 443 ssl http2;
    server_name raptor.example.com;


ssl_certificate     /etc/ssl/certs/raptor.pem;
    ssl_certificate_key /etc/ssl/private/raptor.key;



location / {
        proxy_pass http://127.0.0.1:4000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Caddy example:

raptor.example.com {
    reverse_proxy localhost:4000
}

Caddy handles TLS certificate provisioning automatically via Let's Encrypt.

Authentication

Production deployments must use at least one of:

Option 1: Clerk SSO (Recommended)

Clerk provides managed authentication with SSO, OAuth, and multi-factor support.

  1. Create a Clerk application at clerk.com
  2. Configure OAuth providers (Google, GitHub, etc.) in the Clerk dashboard
  3. Set environment variables:
CLERK_SECRET_KEY=sk_live_...
CLERK_PUBLISHABLE_KEY=pk_live_...
CLERK_DOMAIN=your-app.clerk.accounts.dev
  1. Optionally disable token fallback:
RAPTOR_ALLOW_TOKEN_FALLBACK=false

When Clerk is active, the Control Panel UI uses Clerk's embedded sign-in flow. API requests can authenticate via Clerk session tokens or the RAPTOR_ACCESS_TOKEN (if fallback is enabled).

Option 2: Founder Key

For deployments that do not need multi-user SSO, a Founder Key provides single-operator authentication.

  1. Choose a strong key (32+ characters)
  2. Hash it with SHA-256:
echo -n "your-founder-key" | sha256sum
  1. Set the hash:
RAPTOR_FOUNDER_KEY_HASH=<sha256-hash>
  1. Authenticate via the /api/auth/founder endpoint with the raw key.

Token Auth (Always Active)

RAPTOR_ACCESS_TOKEN is always required and always accepted for API access. Use it for:

  • Machine-to-machine integrations
  • CI/CD pipelines
  • Monitoring and health checks

Pass it as X-Raptor-Token: or Authorization: Bearer .

Secret Management

Never store secrets in .env files on production hosts. Use your platform's secret manager:

| Platform | Secret Manager |
|---|---|
| AWS | Secrets Manager or Parameter Store |
| GCP | Secret Manager |
| Azure | Key Vault |
| Railway | Environment variables (encrypted at rest) |
| Docker Swarm | Docker secrets |
| Kubernetes | Kubernetes secrets (with external-secrets-operator for rotation) |

Secrets to manage:

  • RAPTOR_ACCESS_TOKEN
  • DATABASE_URL (contains credentials)
  • CLERK_SECRET_KEY
  • RAPTOR_FOUNDER_KEY_HASH
  • All provider API keys (ANTHROPIC_API_KEY, OPENAI_API_KEY, etc.)
  • STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET
  • RAPTOR_SIGNING_PRIVATE_KEY

Health Monitoring

Endpoints

| Endpoint | Purpose | Use For |
|---|---|---|
| GET /api/health | Liveness check | Load balancer health probe |
| GET /api/ready | Readiness check (includes DB) | Deployment rollout gate |
| GET /api/health/dependencies | Per-dependency status | Monitoring dashboard |

Alerting

Configure alerts for:

  • /api/health returning non-200 for more than 30 seconds
  • /api/ready returning non-200 for more than 60 seconds
  • Any dependency in /api/health/dependencies reporting unhealthy
  • API response latency exceeding p95 SLO (1 second)

Suggested Monitoring Stack

  • Metrics: Prometheus scraping health endpoints, or your APM tool
  • Logs: Structured JSON logs to stdout, collected by your log aggregator
  • Uptime: External uptime monitor hitting /api/health every 30 seconds

Log Management

Raptor logs to stdout in structured JSON format. In Docker Compose, access logs with:

docker compose logs -f control-panel
docker compose logs -f mcp-server

For production, route logs to a centralized system (Datadog, Grafana Loki, CloudWatch, etc.) using your container runtime's log driver.

SLO Targets

| Metric | Target |
|---|---|
| Availability | 99.5% (measured at /api/health) |
| API latency p50 | < 200 ms |
| API latency p95 | < 1 second |
| RPO (Recovery Point Objective) | < 1 hour |
| RTO (Recovery Time Objective) | < 15 minutes |

These targets assume a properly configured deployment with database backups, health monitoring, and a tested recovery procedure.

Disaster Recovery

Recovery Point Objective (RPO < 1 hour)

Achieve sub-hour RPO with:

  • Managed database PITR: Neon, RDS, or Cloud SQL with continuous WAL archiving
  • Logical backups: Scheduled pg_dump every hour (see Database)
  • Immutable tables: Cannot be lost to application-level errors. Only a database-level disaster requires restore.

Recovery Time Objective (RTO < 15 minutes)

Achieve 15-minute RTO with:

  1. Pre-built container images: Keep the latest image available in your registry. Do not build from source during recovery.
  2. Database restore: Restore from PITR or latest backup. Managed databases restore in under 5 minutes.
  3. Configuration in secret manager: No manual .env assembly during recovery.
  4. Documented runbook: Practice the recovery procedure quarterly.

Recovery Procedure

# 1. Restore database (example: Neon branch restore)

Or: psql < backup.sql



2. Start services

docker compose up -d


3. Verify health

curl http://localhost:4000/api/ready


4. Verify data integrity

curl http://localhost:4000/api/health/dependencies

Deployment

Production deploys happen via git push only. Never use direct deploy commands (railway up or equivalents). Direct deploys break provenance tracking because they bypass the git commit SHA that Raptor embeds in build attestations.

# Correct: deploy via git push
git push origin main


Wrong: direct deploy breaks provenance


railway up  <-- never do this

Scaling

Vertical Scaling

A single control-panel instance handles most workloads. Scale vertically by increasing CPU and memory allocation. The Go runtime efficiently uses available cores.

Horizontal Scaling

To run multiple control-panel replicas:

  1. Use an external PostgreSQL instance (not the bundled container)
  2. Place a load balancer in front of all replicas
  3. Configure health checks on the load balancer using /api/ready
  4. Ensure all replicas share the same RAPTOR_ACCESS_TOKEN and provider keys

The MCP server is stateless and can be scaled independently.

Database Scaling

  • Connection pooling: Use PgBouncer or your provider's built-in pooler for high-replica counts
  • Read replicas: Not currently supported (all queries go to the primary)
  • Storage: Immutable tables grow indefinitely. Plan storage based on inference volume (see Database)

Build Attestation

For supply-chain security, sign builds with an Ed25519 key:

# Generate a signing key
raptor-sign keygen


Set during docker build

docker build \
  --build-arg RAPTOR_SIGNING_PRIVATE_KEY="$(cat signing.key)" \
  -f Dockerfile.control-panel \
  -t raptor-cp .


Verify a signed image

docker run --rm raptor-cp ./raptor-verify

The attestation embeds the git commit SHA, build time, builder version, and binary hash. It is written to .attestation.json inside the container image.
